# subscribe-manager 서비스 정의서

작성일: 2026-10-30 · 상태: 구현 전 검토안

## 1. 목적과 설계 원칙

구독 결제와 생활 속 기한을 한곳에 기록하고, 앞으로 발생할 비용과 행동할 시점을 알려주는 개인용 웹 서비스다. 기본 화면은 통합하되 항목의 성격에 따라 입력 필드, 상태, 계산 방법을 달리한다. 한국 거주 사용자를 첫 대상으로 삼되 국가, 통화, 시간대는 데이터로 보관한다.

| 원칙 | 제품에서의 의미 |
| --- | --- |
| 원본과 추정 분리 | 사용자가 확정한 정보, 영수증으로 확인한 결제, LLM 추출 후보, 검색 기반 소식, 계산된 예상치를 서로 다른 상태로 표시한다. |
| 결제 주체 중심 | ‘Nano Banana’처럼 모델·기능명이 독립 결제 상품이 아니라면 실제 결제하는 서비스와 요금제 아래 기능·관심 태그로 연결한다. 결제 서비스가 확인되지 않으면 후보로만 둔다. |
| 빈칸은 빈칸으로 | 이미지에 없는 금액·날짜·조건은 추정해 확정하지 않는다. 날짜가 불명확하면 확인 가능한 정밀도만 저장하고, 정확한 날짜가 필요한 알림과 비용 계산에서는 제외하거나 추가 입력을 요청한다. |
| 사용자가 최종 결정 | 이미지 추출, 해지 정보, 소식, OTT 추천은 검토를 돕는다. 자동 결제 확인·자동 해지·자동 구매는 하지 않는다. |
| 동일 데이터의 여러 보기 | 홈, 목록, 캘린더, 리포트는 같은 관리 항목과 이벤트를 다른 관점에서 보여준다. |

### 관리 범위

- **구독:** OTT, AI, 디자인·생산성, 쇼핑·배달 멤버십, 게임, 음악·독서·강의, 가전 구독, 정기배송 및 사용자가 직접 등록한 서비스. 서비스 카탈로그에 없어도 사용자 정의 이름으로 등록한다.
- **생활 기한:** 기프티콘·쿠폰·상품권, 포인트, 멤버십 만료, 제품 보증, 보장 서비스, 임의의 검토·갱신 기한. 반복 결제가 없는 항목에 결제 주기를 강요하지 않는다.
- **중복 성격:** 유료 멤버십은 구독 항목 하나로 관리하고 만료·갱신 이벤트를 그 항목에 연결한다. 별도 생활 기한 항목을 자동으로 만들지 않는다. 사용자가 다른 목적의 별도 항목을 만들면 중복 가능성을 안내한다.

## 2. 정보 구조와 화면

| 화면 | 핵심 내용과 행동 |
| --- | --- |
| 통합 홈 | 오늘·이번 주·이번 달의 결제, 해지 마감, 검토일, 갱신일, 만료일을 시간순으로 표시한다. D-day와 이벤트 유형, 실제/예상 금액, 확인 필요 표시를 함께 보여준다. 빠른 등록, 사용 완료, 기간 연장, 해지 예정/완료로 이동한다. |
| 항목 목록·상세 | 구독/생활 기한 탭과 유형·카테고리·상태·기한 필터. 상세에는 원본 이미지, 가격·날짜 이력, 관련 이벤트·알림, 결제 확인 내역, 해지 경로 또는 이용 조건을 보여준다. |
| 등록·검토 | 입력 폼을 통한 직접 등록과 이미지 업로드를 통한 등록 보조 진입점. 유형을 먼저 고르고 해당 필드만 표시한다. 이미지 추출 후보는 원본과 나란히 보여주며 필드별 근거·미확인 항목을 수정한 뒤 저장한다. 문장이나 대화로 등록하는 기능은 제공하지 않는다. |
| 캘린더 | 월간·주간·목록 보기. 이벤트 유형별 색상/필터, 같은 날의 여러 이벤트, 반복 결제의 미래 발생일, Google Calendar 연동 상태를 제공한다. |
| 알림함·설정 | 앱 내 알림 내역, 항목별 기본 알림 시점, 기기별 푸시 구독과 권한 상태, 시간대·조용한 시간, Google Calendar 연결을 관리한다. |
| 지출 리포트 | 월별 현금 유출과 월 환산 비용을 분리하고, 실제·예상 범례, 서비스별 표/그래프, 이력 비교, 서비스 구체 시각화를 제공한다. |
| 해지 안내 | 결제 경로별 공식 절차, 검증된 링크, 출처·확인일·확인되지 않은 조건, 사용자의 해지 상태와 마감일을 표시한다. |
| 서비스 소식 | 내 구독·요금제와의 관련성, 변경 전후, 적용 대상, 출처, 발표일·적용일, 미확인 사항을 표시한다. 검색 상태도 보여준다. |
| OTT 탐색·추천 | 취향 설문, 관심 작품, 작품별 확인된 국내 제공처, OTT 조합 선택, 유일하게 볼 수 있는 작품 수, 다음 청구 주기 예상 비용 차이와 추천 이유. |
| 사용 완료·휴지통 | 사용 완료한 기프티콘 이미지의 남은 보관 기간, 복원, 즉시 삭제. 이미지가 지워진 이후에도 남는 사용 이력의 범위를 안내한다. |

모바일에서는 홈의 다가오는 이벤트와 등록을 우선 노출한다. 모든 상태는 색만으로 구분하지 않고 텍스트를 병기한다. 구체 시각화에는 키보드 탐색·동작 줄이기 설정과 표 대체 보기를 제공한다.

## 3. 입력 방식과 항목별 필드

| 유형 | 필수 확인 항목 | 관련 선택 항목 |
| --- | --- | --- |
| 반복 결제 구독 | 서비스 이름, 상태, 결제 주기, 금액 또는 ‘미확인’ | 요금제, 결제 경로, 통화, 최초 가입일, 다음 결제일, 갱신일, 해지 마감일, 검토일, 종료일, 자동 갱신 여부, 부가 조건 |
| 기간제 구독·멤버십 | 이름, 시작/종료 기준 또는 ‘미확인’ | 선불 금액, 재가입/연장 기록, 결제 경로, 갱신 방식 |
| 쿠폰·기프티콘·상품권 | 이름, 사용 상태, 만료일 또는 ‘미확인’ | 사용처, 액면가/잔액, 이용 조건, 바코드 포함 원본, 사용일 |
| 포인트·보증·보장·기타 기한 | 이름, 기한 또는 ‘미확인’ | 사용처·제품, 구매일, 보장 범위, 알림 시점, 증빙 이미지 |

금액은 `amount + currency + 의미(청구액/액면가/잔액)`로 저장한다. 가격과 요금제가 바뀌면 과거 값을 덮지 않고 적용 시작일이 있는 이력을 추가한다. 결제 주기는 월·연·주·사용자 지정 간격과 선불/1회성으로 표현하며, 무료 체험과 할인 종료일도 별도 이벤트로 기록할 수 있다.

### 날짜의 구분

| 날짜 | 정의와 동작 |
| --- | --- |
| 최초 가입일 | 첫 계약·사용 시작의 기록. 다음 결제일의 대용으로 사용하지 않는다. |
| 다음 결제일 | 앞으로 청구될 것으로 예상되는 날. 명시되지 않았다면 임의 계산으로 확정하지 않는다. |
| 갱신일 | 이용 권한이나 계약 기간이 새로 시작/연장되는 날. 결제일과 같을 수도 다를 수도 있다. |
| 계약상 해지 마감일 | 다음 청구·갱신을 피하기 위해 해지해야 하는 마지막 날. 공식 조건 또는 사용자 입력 근거가 없으면 ‘미확인’. |
| 검토일 | 사용자가 유지 여부를 판단하기로 정한 날. 서비스 정책의 해지 마감일로 취급하지 않는다. |
| 만료·보장 종료일 | 사용·보장 권한의 마지막 날. 날짜만 있으면 사용자 시간대의 종일 이벤트로 취급하고 종료 시각은 단정하지 않는다. |
| 알림 시점 | 위 이벤트별 상대 시점 또는 지정 시각. 업무 날짜 자체와 별도 저장한다. |

기본 시간대는 `Asia/Seoul`, 변경 가능. 날짜만 있는 경우 D-day는 해당 시간대의 달력 날짜 차이로 계산한다. 월말 결제는 ‘원래 31일’이라는 기준일을 보존하고 해당 월 마지막 날로 보정하는 정책을 기본 추천한다. 실제 청구일이 달라지면 사용자가 다음 결제일을 수정할 수 있게 한다. 2월 29일의 연간 반복도 해당 연도 마지막 날로 보정하되 표시한다. 반복 규칙은 예상 이벤트 생성용이며 실제 결제 증거가 아니다.

날짜는 확인 가능한 정밀도를 함께 저장한다. `2025년`, `2025년 1월`, `2025년 1월 15일`, 정확한 시각이 있는 값은 각각 `연`, `연·월`, `날짜`, `날짜·시각` 정밀도로 구분한다. 예를 들어 이미지에 `2025년 1월부터 멤버십`이라고만 표시되면 `2025-01`과 `연·월` 정밀도를 저장하며 1월 1일 같은 특정 날짜로 바꾸지 않는다. 연·월까지만 확인된 값은 월 단위 이력 표시에 사용할 수 있지만, 정확한 결제일·D-day·알림 예약에는 사용하지 않고 사용자의 추가 입력을 요청한다.

### 등록 경로

등록 방식은 다음 두 가지만 제공한다. 문장이나 대화로 구독 정보를 등록하는 기능은 제공하지 않는다.

1. **입력 폼을 통한 직접 등록:** 관리 유형 선택 → 해당 유형에 필요한 필드 입력 → 날짜 의미·반복·알림 미리보기 → 저장. 구독에는 서비스명·요금제·금액·결제 주기·가입일·다음 결제일 등을, 기프티콘에는 사용처·액면가·만료일 등을, 보증에는 제품·구매일·보장 종료일 등을 보여준다. 불명확한 필드는 `모름/나중에 확인`으로 둘 수 있다.
2. **이미지 업로드를 통한 등록 보조:** 이미지 업로드 → 비공개 임시 저장 → OpenAI 이미지 이해 모델로 화면에 보이는 후보 추출 → 해당 관리 유형의 입력 폼에 초안 채우기 → 원본과 초안을 나란히 검토 → 누락값 입력·오류 수정 → 사용자 확정 후 저장. 처리 실패 시 원본을 유지하고 빈 입력 폼과 재시도를 제공한다.

이미지 입력은 결제 영수증뿐 아니라 서비스 계정·멤버십 화면, 구독 관리·요금제 화면, 다음 결제일·갱신일 안내, 결제 내역·안내 메시지, 기프티콘·쿠폰·상품권, 멤버십·보증기간 안내 화면을 지원한다. 추출 대상은 등록에 필요한 서비스명, 요금제, 사용처, 금액, 결제·갱신·만료 시점, 청구 경로와 이용 조건이다.

예를 들어 넷플릭스 화면에서 `광고형 스탠다드 멤버십`, `2025년 1월부터`, `네이버 멤버십 서비스 추가 옵션을 통해 청구`가 보이면 서비스명, 요금제, 연·월 정밀도의 멤버십 시작 시점, 청구 경로 문구를 후보로 채운다. 화면에 없는 정확한 가입일, 결제 금액, 결제 주기, 다음 결제일은 비워 두고 추가 입력을 요청한다. `네이버 멤버십을 통해 청구`라는 문구만으로 무료 이용, 할인 여부나 할인 금액을 확정하지 않는다.

OpenAI의 이미지 입력/분석 기능과 스키마에 맞는 구조화 출력은 이 흐름에 적합하다. 다만 이미지 글자 판독은 오류가 가능하므로 필드의 `원문 조각/위치(가능한 경우)`, `값의 정밀도`, `추출 상태`, `사용자 확정 여부`를 보관하고 사용자 확인을 필수로 둔다. 이메일, 전화번호, 계정 ID, 주소처럼 등록 목적에 필요하지 않은 개인정보는 추출 스키마에서 제외하고 저장하지 않는다. 모델 응답에 포함되더라도 서버의 허용 필드 검증 단계에서 버린다. 이미지 생성 API가 필요한 기능은 아니다. [OpenAI 이미지 입력 문서](https://developers.openai.com/api/docs/guides/images-vision), [구조화 출력 문서](https://developers.openai.com/api/docs/guides/structured-outputs).

## 4. 상태, 원본 이미지와 휴지통

구독 상태는 `활성 → 해지 예정 → 해지 완료(이용 가능 종료일 대기) → 종료`를 기본으로 한다. 사용자가 확인한 해지 완료만 실제 해지로 기록한다. 만료 또는 종료 뒤 재가입하면 같은 서비스 아래 새 **가입 기간**을 만든다. 갱신이나 일시 중지는 별도 이력 이벤트로 남긴다.

쿠폰류의 사용 상태(`미사용/일부 사용/사용 완료/만료`)와 이미지 보관 상태(`보관/휴지통/영구 삭제`)는 독립이다. ‘사용 완료’를 누르면 사용일을 기록하고 이미지를 휴지통으로 이동한다. 사용 이력 항목은 남겨 중복 사용 방지와 과거 기록 조회에 활용한다. 휴지통에 들어간 원본은 **이동한 시각부터 30일** 동안 복원할 수 있으며, 복원은 이미지 보관 상태만 되돌린다. 복원하면 기존 자동 삭제 예정은 취소한다. 사용 완료를 취소하려면 사용 상태를 별도로 정정한다. 30일 후 백그라운드 작업이 원본과 파생 이미지를 삭제하고 `영구 삭제` 시각만 메타데이터에 남긴다. 사용자는 휴지통에서 즉시 영구 삭제도 할 수 있다.

구독 계정·요금제·결제 스크린샷은 추출 결과를 확인할 때 `원본 계속 보관` 여부를 선택하게 한다. 기본 추천은 개인정보 노출을 줄이기 위해 **추출 결과 저장 후 원본 삭제**이며, 보관을 선택하면 상세 화면에서 다시 볼 수 있다. 원본을 보관하지 않는 경우 항목 저장이 성공한 뒤 원본과 파생 이미지를 삭제한다. 보증서처럼 나중에 증빙으로 필요할 수 있는 이미지는 기본 보관을 제안한다. 보관 중인 구독·보증 이미지를 사용자가 삭제하면 먼저 휴지통으로 보내고, 이동 시점부터 30일 동안 복원 또는 즉시 삭제할 수 있게 한다.

이미지 삭제와 관리 항목·구독 이력 삭제는 서로 다른 작업이다. 이미지가 삭제되어도 사용 이력에는 이름, 사용처, 사용일, 액면가/사용 금액, 상태 변경 기록을 남기고 구독 이력에는 사용자가 확정한 요금제·날짜·가격 기록을 남긴다. 바코드와 이미지에서 추출된 민감 원문, 임시 추출 자료는 이미지 영구 삭제 시 함께 삭제하는 것을 기본으로 한다. 사용자가 관리 항목 자체를 삭제하면 별도의 항목 삭제·복구 정책을 적용한다. 이미지가 영구 삭제되면 원본 복구는 불가하다는 점을 삭제 전에 표시한다.

원본은 Supabase Storage의 **private bucket**에 사용자별 경로로 저장하고 DB와 Storage 양쪽에서 소유자 접근 규칙(RLS)을 적용한다. 보기는 짧게 유효한 서명 URL 또는 인증된 요청으로 제공한다. 바코드·금액이 있는 이미지를 공개 버킷이나 푸시 알림 본문에 넣지 않는다. 서버 측 OpenAI API 키와 Storage 권한 키는 브라우저에 노출하지 않는다. [Supabase 비공개 버킷 문서](https://supabase.com/docs/guides/storage/buckets/fundamentals), [Storage 접근 제어 문서](https://supabase.com/docs/guides/storage/security/access-control).

## 5. 통합 일정과 알림

항목에서 날짜별 **이벤트**를 만든다: 결제, 갱신, 계약상 해지 마감, 사용자 검토, 만료, 할인/무료 체험 종료. 하나의 항목에 같은 날 여러 이벤트가 있어도 각각의 의미를 표시한다. 반복 이벤트는 확인 가능한 범위(예: 향후 12개월)만 생성하고 요금·주기·종료일 변경 시 재계산한다. 과거 확정 기록은 재계산하지 않는다. 알림 작업은 이벤트 ID와 알림 시점을 키로 중복 발송을 막고, 일정 변경·상태 종료·권한 철회 시 다시 예약하거나 취소한다.

| 채널 | 기능과 한계 |
| --- | --- |
| 앱 내 알림 | 사용자 계정의 알림함에 기록. 웹사이트 접속 시 확인 가능하며 읽음/보류 처리를 지원한다. 푸시 실패와 별개로 유지한다. |
| Web Push | 동의한 기기의 브라우저/PWA로 발송. HTTPS, 서비스 워커, 기기별 구독과 알림 권한이 필요하다. iOS·iPadOS는 지원 버전에서 홈 화면에 추가한 웹 앱에 Web Push를 제공한다. 설치만으로 권한이 자동 부여되지는 않는다. 전달 시각은 기기·네트워크·권한에 영향을 받으므로 정확한 도착을 보증하지 않는다. |
| 외부 알림 | 이메일·메신저 등은 별도 연동/동의가 필요한 후속 범위. 앱 내 알림이나 Web Push와 같은 채널로 취급하지 않는다. |
| Google Calendar 알림 | Google에 내보낸 일정의 알림 설정에 따라 Google이 발송한다. 앱 내/푸시 발송 기록과 별개이며 중복 수신 가능성을 설정 화면에 설명한다. |

알림 기본값은 사용자 설정으로 두고, 결제·해지 마감·만료별로 다른 상대 시점을 선택할 수 있게 한다. 예: 7일 전/3일 전/당일, 시각은 사용자 시간대 기준. 권한 거부 또는 푸시 구독 만료 시 앱 내 알림은 유지하고 재설정 안내를 제공한다. [MDN 알림 권한/보안 컨텍스트](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API), [WebKit iOS 홈 화면 웹 앱 Web Push](https://webkit.org/blog/13878/).

### Google Calendar: 권장안은 단방향 내보내기

앱 데이터를 원본으로 하고 사용자가 선택한 이벤트만 Google Calendar에 생성·수정·삭제한다. 초기 버전은 앱 전용 보조 캘린더를 권장한다. 이유는 사용자 개인 일정과 분리되고 연동 해제 시 처리 범위를 명확히 할 수 있기 때문이다. 연결 시 OAuth 동의와 필요한 최소 권한을 요청하고, 토큰은 서버에 암호화 저장한다. 사용자별 `앱 이벤트 ID ↔ Google 캘린더/이벤트 ID` 매핑과 마지막 반영 상태를 보관하며, 재시도 시 기존 이벤트를 갱신해 중복 생성을 피한다. 앱에서 날짜 변경·종료·삭제 시 매핑된 일정만 갱신·삭제한다. [Google Calendar 권한 범위](https://developers.google.com/workspace/calendar/api/auth), [일정 ID와 중복 방지](https://developers.google.com/workspace/calendar/api/guides/create-events), [확장 속성](https://developers.google.com/workspace/calendar/api/guides/extended-properties).

Google Calendar에서 사용자가 내보낸 일정을 수정해도 앱으로 가져오지 않는다. 다음 동기화 때 앱 값으로 되돌아갈 수 있음을 화면에 설명한다. Google에서 일정을 직접 삭제하면 다음 동기화 때 다시 생성될 수 있으므로 앱에서 해당 이벤트의 내보내기를 끄도록 안내한다. 연동 해제 시 ‘내보낸 일정 삭제’와 ‘Google에 남기기’를 선택하게 하고, 어느 쪽이든 OAuth 토큰·동기화 작업을 중단한다. 인증 만료·권한 철회·API 오류는 `연결 재인증 필요/동기화 지연` 상태로 표시하고 재시도하되 앱 내부 일정과 알림에는 영향을 주지 않는다. 양방향 동기화는 편집 충돌·삭제 충돌·증분 동기화 관리가 필요한 후속 기능으로 유보한다. [Google Calendar 증분 동기화 문서](https://developers.google.com/workspace/calendar/api/guides/sync).

## 6. 지출·기간 리포트

비용의 근거를 세 갈래로 분리한다.

| 근거 | 표시/계산 |
| --- | --- |
| 실제 결제 | 사용자가 기록하거나 영수증을 확인한 결제 거래만 해당 월·연도 실제 지출에 합산한다. 환불은 별도 음수 거래로 반영한다. 은행/카드 연동이 없으면 실제 결제 내역의 완전성을 주장하지 않는다. |
| 예정 청구 | 활성 가입 기간의 다음 결제일, 유효한 가격 구간, 결제 주기로 향후 예상 청구를 생성한다. 할인 종료·가격 변경·미확인 갱신은 별도 표시하거나 계산에서 제외한다. |
| 월 환산 비용 | 서비스 간 크기 비교용으로 반복 가격을 월 단위로 환산한다(예: 연 결제액 ÷ 12). 실제 해당 월의 현금 유출이 아니다. 사용량 기반·가격 미확인 항목은 환산하지 않는다. |

대시보드에는 `이번 달 실제 결제`, `이번 달 남은 예상 결제`, `현재 활성 구독 월 환산액`, `다음 청구 주기 예상액`을 구분해 보여준다. 전체/서비스별 월간·연간 지출, 다음 결제 예정액, 서비스별 누적 실제 지출과 확인 가능한 기록 시작일을 제공한다. 과거 기록이 없는 구간은 ‘데이터 없음’이며 현재 요금으로 과거를 소급해 실제 지출로 채우지 않는다. 구독 기간과 재가입 횟수는 가입 기간 이력으로 계산하고, 종료 후 재가입은 연속 사용으로 합치지 않는다. 현재/과거 비교는 같은 기준(실제·예상·월 환산)을 선택했을 때만 한다. 모든 금액은 원통화로 보관하며 다른 통화의 합계는 환율 기준일·출처가 준비되기 전에는 단순 합산하지 않는다.

Originkit의 [Rubber Spheres 참고 화면](https://www.originkit.dev/components/rubber-spheres?preset=base)은 시각적 영감으로 둔다. 해당 개별 페이지는 정의서 작성 시점에 확인되지 않아 구현 가능 여부·라이선스·세부 상호작용은 도입 전에 재검토한다. 제품상 구 하나는 **서비스 하나**를 나타내고, 재가입을 포함한 가입 기간은 상세 이력에 묶는다. 크기 기준을 `월 환산액 / 확인된 누적 지출 / 가입 개월 수`로 전환하고, 선택한 기준과 단위를 항상 표시한다. 크기는 극단값 때문에 작은 서비스가 사라지지 않도록 제한된 범위로 정규화한다. 색/윤곽은 활성·종료·자료 부족을 구분한다. 선택 시 요금, 실제/예상 구분, 다음 결제일, 가격·가입 이력을 연다. 활성/종료 전환과 동일한 정렬·필터를 표와 막대/추세 그래프에 제공해 정확한 비교를 보완한다. 실제 서비스 사용 횟수는 사용자가 따로 기록하거나 정식 연동하지 않으면 보여주지 않는다.

## 7. 해지 안내

해지 안내는 `(서비스, 국가, 결제 경로, 요금제/상품, 확인일)` 단위로 관리한다. 결제 경로는 공식 웹, Apple App Store, Google Play, 통신사/제휴, 오프라인·기타로 구분한다. 사용자가 결제 경로를 모르면 먼저 확인하도록 안내한다.

검색 가능한 LLM은 공식 서비스 도움말/정책과 해당 결제 플랫폼의 공식 문서를 우선 검색한다. 저장 전 출처 URL이 실제 열리고 서비스·경로·지역과 일치하는지 검증한다. 화면에는 확인된 메뉴 경로, 검증된 관리/해지 링크가 있으면 그 링크, 확인된 해지 조건·이용 종료 시점, 출처와 마지막 확인일을 보여준다. 직접 해지 링크를 확인하지 못하면 공식 도움말 링크와 메뉴 이동 경로만 제공한다. 조건·환불·종료 시점이 출처에 없으면 `확인 필요`로 둔다. 오래된 안내는 재검색하거나 재확인 표시를 한다. LLM이 새 URL을 조합하거나 절차를 만들어내지 않는다.

사용자는 `해지 검토/해지 예정/사용자가 확인한 해지 완료/종료`를 별도로 기록한다. ‘해지 안내 열기’나 ‘해지 예정’만으로 구독이 해지된 것으로 처리하지 않는다. 실제 해지 작업은 서비스 제공자의 화면에서 사용자가 수행한다.

## 8. 최신 소식 수집과 개인화

개별 서비스 API를 필수로 삼지 않고 웹 검색이 가능한 LLM과 검증 단계로 소식을 수집한다. 공통 소식은 서비스별로 한 번 수집·정규화해 DB에 저장하고, 사용자에게 보여줄 때 해당 구독의 국가·결제 경로·요금제·관심사에 맞춰 관련성을 판단한다. OTT 공개 예정/추가 작품, AI 모델·한도·요금제, 디자인 기능, 게임 입·출고, 쇼핑 혜택·가격, 음악·독서·강의 콘텐츠, 가전 상품·관리 조건의 변경을 유형화한다.

수집 흐름: 서비스별 일정 또는 요청 시 검색 → 공식 발표·서비스 페이지 우선 수집 → 문서 접근 및 날짜·대상 확인 → 같은 발표의 중복 병합 → 공통 소식 저장 → 사용자별 적용 가능성 평가 → 카드에 출처·확인 시각·불확실성 표시. 제목만 비슷한 기사를 중복 소식으로 확정하지 않도록 출처 URL, 발표 주체, 적용일과 내용으로 병합한다. 검색 결과의 원문 전체를 무단 복제하지 않고 짧은 요약과 링크를 저장한다. 가격·혜택·요금제 적용 여부는 공식 근거가 없으면 단정하지 않는다.

저장 단위는 서비스 ID, 소식 유형, 제목·요약·변경 전후, 출처 URL과 출처 유형, 발표일, 실제 적용일, 국가·요금제·신규/기존 가입자 등 대상 조건, 마지막 확인 시각, 미확인 사항, 검증 상태다. 사용자별로는 `적용 확인/적용 가능성 있음/대상 아님/확인 필요`와 판단 근거를 따로 기록한다. 소식이 없다는 이유만으로 서비스에 변화가 없다고 단정하지 않는다.

| 검색 결과 | 사용자에게 보여줄 상태 |
| --- | --- |
| 검색·원문 접근 실패 | ‘소식을 확인하지 못함’ + 재시도 예정 시각. |
| 검색 성공, 범위 내 신규 항목 없음 | ‘최근 확인한 범위에서 새 소식 없음’ + 검색 범위·확인 시각. |
| 소식은 있으나 요금제·국가·가입 조건 불명 | 소식 자체는 표시하고 개인 적용 여부는 ‘확인 필요’. |
| 확인 가능한 변경 | 출처, 발표일·적용일, 내 요금제와의 관련 이유를 함께 표시. |

예: 새 AI 모델 발표가 확인돼도 가입 요금제에서 사용 가능한지 별도 검증한다. 새 멤버십 혜택이 기존 가입자에게 적용되는지도 마찬가지다. 수집 주기·재확인 주기·검색 비용 예산은 서비스 유형과 변경 빈도에 맞춰 운영 설정으로 둔다.

## 9. 취향 기반 OTT 추천

첫 설문은 선호/비선호 장르, 좋아하는 작품, 월 예산, 현재 OTT, 사용자가 입력한 시청 빈도·이용 상황을 받는다. 작품의 ‘보고 싶어요’와 시청 완료 여부를 분리한다. OTT 외 소식에도 `써보고 싶어요`, `이 혜택에 관심 있어요` 같은 반응을 저장해 소식 정렬과 검토일 제안에 활용하되 실제 사용 증거로 취급하지 않는다.

작품 데이터는 작품 ID와 지역별 OTT 제공 기록을 분리한다. 제공 기록에는 국가, OTT, 공개/제공 시작·종료 예정일, 확인한 출처·시각, `제공 확인/예정 확인/미확인/제공 종료 확인` 상태를 둔다. 일반 작품 공개일을 국내 OTT 제공일로 변환하지 않는다. 주요 공개 예정작 검색 결과는 전체 편성표가 아니며, 검색 결과에 없는 작품은 ‘제공처 미확인’이지 ‘볼 수 없음’이 아니다. 복수 OTT에 있는 한 작품은 한 번만 센다.

추천은 초기에는 설명 가능한 규칙으로 계산한다.

1. 사용자가 선택한 OTT 조합에 대해 **국내 제공이 확인된** 관심 작품의 합집합을 구한다. 제공처 미확인 작품은 별도 목록으로 뺀다.
2. 조합별 유일 관심 작품 수, 선호 장르·좋아하는 작품에 따른 가중 점수, 사용자 입력 이용 상황을 보여준다. 관심 표시가 적다는 사실만으로 해지를 추천하지 않는다.
3. 선택한 서비스의 유효한 요금제·다음 갱신일을 이용해 `다음 청구 주기 예상액`을 계산한다. 현재 조합과 선택 조합의 **향후 예상 지출 차이**를 표시한다. 이미 결제한 금액의 환불이나 확정 절약액으로 쓰지 않는다.
4. 예산 안에서 관심 작품 커버리지와 비용의 균형이 좋은 조합을 몇 개 제안한다. 여러 후보가 비슷하면 사용자가 입력한 이용 빈도, 장기 선호, 해지 마감일, 재가입 불편을 함께 설명한다.

OTT 토글을 바꾸면 확인된 시청 가능 관심 작품, 선택 조합에서 제공이 확인되지 않은 작품(‘볼 수 없음’이라고 단정하지 않음), 비용·현재 조합과의 차이, 근거가 동시에 바뀐다. `현재 보유 조합`과 `가정 조합`을 명확히 구분한다. 콘텐츠 제공 정보가 부족하거나 요금제가 미확인인 서비스는 정확한 최적 조합이라고 주장하지 않고 부족한 정보를 표시한다.

## 10. 데이터 모델 초안

Supabase Postgres와 Auth를 계정·관계형 데이터에, Storage를 이미지 원본에 사용한다. React는 UI, FastAPI는 사용자 권한 검사, OpenAI 호출, 검색·검증, 일정·알림·삭제 작업의 서버 경계다. 인증/권한은 사용자 ID 기준으로 DB RLS와 서버 검증을 함께 적용한다. 백그라운드 작업은 재시도와 중복 방지 키를 갖는다.

| 엔터티 | 핵심 속성/관계 |
| --- | --- |
| `users`, `preferences` | 사용자 ID, 시간대·통화, 알림 기본값, OTT 취향/예산. |
| `services`, `plans`, `features` | 서비스 카탈로그와 사용자 정의 서비스, 실제 요금제, 그 아래 모델·기능. 사용자 정의 이름을 카탈로그 사실로 승격하지 않는다. |
| `items` | 사용자 ID, 구독/생활 기한 유형, 세부 분류, 제목, 상태, 메모, 서비스·요금제 참조(선택). |
| `subscription_periods`, `price_periods` | 가입·종료·재가입 기간과 날짜별 요금·주기·통화 이력. |
| `item_dates`, `occurrences` | 날짜 의미별 원본 값·정밀도(연/연·월/날짜/날짜·시각)·출처·확정 상태, 생성된 미래 이벤트와 사용자가 고친 예외. |
| `payments` | 실제 결제·환불 거래, 일시·금액·통화·증빙·확정자. 추정 이벤트와 별개. |
| `attachments`, `extraction_drafts` | 비공개 Storage 경로, 파일 종류, 원본 보관 선택, 이미지 보관/휴지통/삭제 상태와 이동·자동 삭제 시각, 허용 필드의 추출 후보·근거·정밀도·확정 여부. |
| `reminder_rules`, `notifications`, `push_subscriptions` | 이벤트별 규칙, 앱 내/푸시 발송 상태, 기기별 구독·권한 정보. |
| `calendar_connections`, `calendar_event_links` | 사용자 OAuth 연결 상태, 내보내기 옵션, 앱/Google 이벤트 매핑·오류 상태. |
| `cancel_guides`, `guide_sources` | 서비스·국가·결제 경로별 절차, 공식 출처, 검증·재확인 시각, 미확인 조건. |
| `news`, `news_sources`, `news_relevance` | 공통 소식·출처·적용 조건과 사용자별 적용 판단. |
| `titles`, `title_availability`, `reactions` | 작품, 국가·OTT별 제공 근거·상태, 보고 싶어요/써보고 싶어요/혜택 관심. |
| `audit_events` | 사용 완료·해지·기간 연장·가격 변경·이미지 삭제 등 상태 변경의 최소 이력. |

출처는 최소 `사용자 직접 입력/이미지 추출 후보/사용자 확인 이미지/검색 자료/계산값`으로 구분한다. 각 날짜와 금액에는 출처·확정 상태·변경 시각을 연결한다. 사용자별 기록과 공통 서비스/소식 데이터를 분리해 다른 사용자의 구독·이미지가 노출되지 않게 한다.

## 11. 주요 처리 흐름

| 상황 | 처리 순서와 실패 처리 |
| --- | --- |
| 이미지 등록 | 업로드 → private Storage → 필요한 필드만 추출 → 입력 폼 초안 → 원본과 후보 검토 → 누락값 입력·오류 수정 → 사용자 저장 → 이벤트/알림 생성 → 원본 보관 선택 적용. 추출 실패 시 직접 입력·재시도, 취소한 임시 파일은 정리. |
| 결제일 수정·기간 연장 | 원본 날짜/가격 이력 변경 → 미래 이벤트·알림 재생성 → 캘린더 내보내기 갱신 → 예상 리포트 재계산. 이미 확인된 실제 결제는 유지. |
| 구독 해지 | 해지 예정 기록 → 사용자가 실제 해지 후 완료 기록 → 이용 가능 종료일까지 유지 → 종료. 결제/갱신 이벤트는 사용자 확인 정보에 맞춰 중단. |
| 쿠폰 사용 완료 | 사용일·상태 기록 → 이미지 휴지통 이동 → 30일 복원 가능 → 기한 경과 후 원본 삭제. 삭제 작업 실패 시 재시도하고 예정 시각·오류를 관리. |
| 새 소식 | 서비스별 검색 → 근거 검증·공통 저장 → 요금제/국가 관련성 평가 → 사용자 카드 표시. 검색 실패·무소식·조건 불명은 각각 다른 상태. |
| OTT 조합 변경 | 선택 조합 → 확인된 작품 제공처 합집합과 미래 청구 계산 → 비교/근거 갱신. 실제 구독 상태·결제 기록은 바뀌지 않는다. |

## 12. 권장 단계와 검토 기준

| 단계 | 범위 | 완료 판단 |
| --- | --- | --- |
| 1. 기본 관리 | 로그인, 수동 등록, 상태/날짜 의미, 통합 홈·목록·캘린더, 앱 내 알림, 실제 결제 수동 기록, 기본 리포트, 비공개 이미지와 휴지통 | 구독·쿠폰·보증 항목을 서로 다른 필드로 등록하고, 알림과 실제/예상 비용이 구분된다. 사용 완료 이미지가 30일 정책에 따라 복원·삭제된다. |
| 2. 입력·연동 | 이미지 추출·입력 폼 검토, Web Push, Google Calendar 단방향 내보내기 | 부분 날짜가 임의의 날짜로 바뀌지 않고 누락 정보와 불필요한 개인정보가 저장되지 않으며, 권한 거부·인증 만료·중복 재시도에도 앱의 원본 기록이 유지된다. |
| 3. 정보·추천 | 공식 해지 안내, 서비스별 소식 수집, OTT 작품/취향·조합 추천, 구 시각화 | 출처·확인일·적용 대상·미확인이 보이며, 중복 작품과 이미 지불한 금액을 절약액에 잘못 반영하지 않는다. |

출시 전 결정할 정책은 첫 지원 국가/통화, 기본 알림 시점, 소식 수집 비용·주기, 공식 작품 제공 데이터의 범위, 이미지/결제 이력의 계정 탈퇴 시 삭제 범위다. 현재 추천값은 **한국·원화·Asia/Seoul을 기본값으로 시작하고 사용자가 변경 가능**, 알림은 항목별 선택, 검색과 이미지 추출은 사용량·비용 한도를 두는 것이다. 이 정의서는 제품 동작을 정하기 위한 초안이며 제공처·가격·해지 절차의 현재 사실을 확정한 카탈로그가 아니다.
