# subscribe-manager MVP 정의서

작성일: 2026-11-02

문서 상태: 구현 전 검토안

## 1. 서비스 목표

`subscribe-manager`는 구독 결제와 생활 속 기한을 한곳에서 관리하는 웹 서비스다.

관리 대상은 OTT나 디지털 서비스에 한정하지 않는다. AI·디자인 도구, 쇼핑·배달 멤버십, 게임·음악·독서·강의, 가전 구독, 정기 배송뿐 아니라 기프티콘, 쿠폰, 포인트, 보증기간, 보장 서비스 종료일도 포함한다.

구독과 생활 기한은 입력 항목과 상태가 다르다. 등록 화면에서는 유형에 맞는 정보를 받고, 홈·캘린더·알림에서는 다가오는 결제와 만료를 함께 보여준다.

서비스가 답해야 하는 핵심 질문은 다음과 같다.

1. 곧 결제·갱신·만료되는 항목은 무엇인가?
2. 실제로 결제한 금액과 앞으로 결제될 금액은 얼마인가?
3. 결제·만료·해지 마감 전에 언제 행동해야 하는가?
4. 하나의 결제로 어떤 서비스와 혜택을 이용하고 있는가?
5. 공식 자료에서 확인된 해지 방법과 최신 변경 사항은 무엇인가?
6. 관심 작품과 예산을 기준으로 어떤 OTT 조합이 적합한가?

## 2. MVP와 후속 기능의 범위

MVP에서는 구독·생활 기한을 등록하고, 다가오는 일정과 예상 비용을 이해하며, 공식 해지 정보와 서비스 소식을 확인하는 흐름을 완성한다. 개발 순서는 의존 관계를 정하기 위한 것이며 뒤 단계에 적힌 MVP 기능을 후속 기능으로 미루는 뜻이 아니다.

| MVP 기능 | 제공 범위 |
| --- | --- |
| 로그인·접근 제한 | 로그인, 사용자별 DB 행·이미지 접근 제한 |
| 통합 관리 | 구독과 생활 기한의 등록·조회·수정·삭제, 상태·이력, 통합 홈과 목록·필터·D-day |
| 직접 등록 | 유형별 입력 폼. 문장·대화형 등록은 제공하지 않음 |
| 이미지 등록 보조 | 계정·멤버십·요금제·결제·쿠폰·보증 화면에서 정보 추출, 원본과 초안 비교, 사용자 확인 후 저장 |
| 캘린더와 알림 | 내부 캘린더, 앱 안 알림, Web Push, 반복 일정과 30일 이미지 삭제 작업 |
| 예상 지출 리포트 | 등록된 요금·주기·날짜에 따른 예상 청구액, 월 환산액, 근거가 있는 추정 누적액 |
| 구 시각화 | 월 환산액·추정 누적액·구독 기간 기준을 전환하는 인터랙티브 구, 표와 일반 그래프 병행 |
| 결합 구독 | 직접 결제·포함 혜택·추가 요금·금액 미확인 관계와 기본 비용 중복 방지 |
| 해지 안내 | 가입·결제 경로별 공식 자료, 검증된 링크·메뉴 경로·출처·마지막 확인일 |
| 최신 소식 | 서비스별 공통 수집, 사용자 구독·요금제·국가·관심사에 맞춘 관련성 표시 |
| Google Calendar | 사용자가 선택한 일정의 단방향 내보내기, 수정·삭제·연결 해제·재인증 처리 |

### 후속 기능

| 후속 기능 | 범위 | MVP에 남는 관련 기능 |
| --- | --- | --- |
| OTT 추천 | 취향 설문, `보고 싶어요`, 추천 점수, OTT 조합 자동 추천, 관심 작품 커버리지와 절약액 시뮬레이션 | OTT 공개 예정작·신규 작품·제공 종료 소식은 MVP 최신 소식에 포함 |
| 결제·환불 거래 처리 | 실제 결제 거래 등록, 영수증과 예상 회차 대사, 부분·분할 결제, 원 결제에 연결된 부분·복수 환불과 귀속 집계 | 구독 금액·주기·다음 결제일, 예상 회차와 예상 지출, 결제 화면 이미지 추출은 MVP에 포함 |

서비스는 실제 금융 거래, 결제 취소, 환불, 구독 해지를 대신 실행하지 않는다. MVP와 후속 기능 모두 사용자가 입력하거나 확인한 정보를 기록하고 분석하는 범위다.

### 그 밖의 확장 후보

- 같은 서비스를 더 저렴하게 이용할 수 있는 공식 결제·할인 경로 비교
- 기한을 제때 처리하거나 불필요한 구독을 검토한 기록을 활용한 게이미피케이션
- 모바일 앱 또는 운영체제의 홈 화면 위젯
- 은행·카드·앱스토어 결제 내역 자동 연동
- 이메일·메신저 알림
- Google Calendar 양방향 동기화

확장 후보도 데이터 구조가 막지 않도록 설계하지만 MVP 완료 조건에는 넣지 않는다.

## 3. 지원 서비스의 범위

직접 등록 범위와 정보 제공 범위는 다르다.

| 지원 수준 | 범위 | 사용자에게 보이는 표시 |
| --- | --- | --- |
| 직접 관리 | 이름이 알려지지 않은 서비스와 사용자 정의 항목을 포함한 모든 구독·생활 기한 | 등록·캘린더·알림·지출 관리 가능 |
| 해지·소식 지원 | 공식 출처와 검색 기준을 정한 서비스 카탈로그 | `해지 안내 지원`, `소식 지원`, 마지막 확인일 표시 |
| 후속 OTT 추천 지원 | 국내 작품 제공 여부와 요금 정보를 확인할 수 있는 OTT | 후속 추천 계산에 포함된 작품·요금의 근거와 확인일 표시 |

카탈로그에 없는 서비스도 직접 등록할 수 있다. 다만 공식 자료나 작품 제공 정보를 확인하지 못한 서비스는 해지 안내·소식과 후속 OTT 추천을 제공한다고 약속하지 않는다. 화면에는 `직접 관리만 가능`, `자료 수집 중`, `정보 확인 필요` 중 하나를 표시한다.

외부 페이지 접근 제한, 지역별 차이, 유료 데이터 계약, 검색 실패로 기능을 완성하기 어려운 경우 해당 서비스를 조용히 제외하지 않는다. 누락 이유와 사용자가 대신 확인할 공식 홈페이지 또는 직접 입력 방법을 제공한다.

### 초기 정보 지원 카탈로그 제안

MVP의 직접 등록은 모든 서비스를 허용하되, 소식·해지 안내는 한국 사용자가 많이 등록할 가능성이 높은 서비스부터 운영 검수가 가능한 수로 시작한다.

| 분야 | 초기 지원 후보 | 최소 제공 범위 |
| --- | --- | --- |
| OTT | 넷플릭스, 티빙, 웨이브, 왓챠, 라프텔, 디즈니+, 쿠팡플레이 | 공식 해지 안내, 가격·정책·주요 공개/신규/종료 소식 |
| AI | ChatGPT, Gemini, Perplexity, Midjourney | 요금제·한도·모델·기능 변경, 공식 결제 경로별 해지 안내 |
| 디자인·생산성 | Adobe, Canva, Microsoft 365, Notion | 가격·기능·AI 기능 변경, 공식 해지 안내 |
| 게임·콘텐츠 | Xbox Game Pass, PlayStation Plus, YouTube Premium, 멜론, 지니뮤직, 밀리의 서재, 클래스101 | 혜택·가격·콘텐츠 변경, 공식 해지 안내 |
| 쇼핑·배달 | 쿠팡 와우, 네이버플러스, 배민클럽, 신세계 유니버스 | 가격·배송·적립·쿠폰 조건 변경, 공식 해지 안내 |
| 가전 구독 | 사용자가 실제 등록한 국내 주요 가전 구독부터 추가 | 상품·관리 서비스·혜택 변경, 공식 해지 안내 |

이 목록은 확정 카탈로그가 아니라 시작 제안이다. 출시 전 공식 자료 접근 가능 여부와 운영 부담을 확인해 최종 목록을 정한다. 가격·해지 조건·제공 종료는 짧은 주기로, 일반 기능 소식은 더 긴 주기로 확인한다. 기본 제안은 가격·해지 조건 7일, 제공 종료 24시간, 일반 기능·콘텐츠 소식 1일이며, 출처의 변경 빈도와 검색 비용에 따라 서비스별로 조정한다.

| --- | --- |
| 통합 홈 | 오늘·이번 주·이번 달 일정, D-day, 예상 지출, 확인 필요 항목, 최신 소식, 빠른 등록 |
| 전체 목록 | 구독·생활 기한, 카테고리·상태·날짜·정보 지원 범위 필터 |

| 등록·검토 | 직접 입력 폼 또는 이미지 업로드, 원본·분석용 이미지와 추출 초안 비교 |
| 내부 캘린더 | 결제·갱신·해지 마감·검토·만료, 월간·주간·목록 보기 |
| 지출 리포트 | 예상 청구액·추정 누적액·월 환산액, 계산 근거와 제외 항목, 표·그래프·구 시각화 |

| 해지 안내 | 결제 경로 선택, 공식 절차, 확인된 링크, 조건, 출처와 마지막 확인일 |
| 서비스 소식 | 내 구독에 미치는 영향, 변경 전후, 대상 국가·요금제, 출처, 미확인 사항 |
| 휴지통 | 이미지의 이동 시각·자동 삭제 예정일, 복원·즉시 삭제 |

상태는 색만으로 전달하지 않고 텍스트를 함께 표시한다. 구 시각화처럼 움직임이 있는 화면에는 동작 줄이기, 키보드 조작, 표 형태의 대체 보기를 제공한다.

OTT 조합 추천 화면은 후속 기능에서 추가한다. OTT 최신 소식은 MVP의 서비스 소식 화면에서 다른 서비스 유형과 함께 제공한다.

## 5. 등록 방식

등록 방식은 입력 폼과 이미지 업로드 두 가지다. 문장이나 대화로 등록하는 기능은 제공하지 않는다.

### 5.1 입력 폼으로 직접 등록

관리 유형을 먼저 선택하고 필요한 필드만 보여준다.

| 관리 유형 | 주요 입력 필드 |
| --- | --- |
| 반복 구독 | 서비스, 요금제, 금액·통화, 결제 주기, 다음 결제일, 가입일, 갱신일, 해지 마감일, 검토일 |
| 기간제 구독·멤버십 | 서비스, 시작·종료 시점, 선불 금액, 갱신 방식, 결제 경로 |
| 기프티콘·쿠폰·상품권 | 이름, 사용처, 액면가·잔액, 만료일, 사용 조건, 원본 이미지 |
| 포인트 | 운영사, 잔액, 만료일, 사용 조건 |
| 보증·보장 서비스 | 제품·서비스, 구매일, 보장 시작·종료일, 보장 범위, 증빙 이미지 |
| 기타 기한 | 이름, 날짜, 반복 여부, 메모, 알림 |

모르는 필드는 비워 두거나 `확인 필요`로 저장할 수 있다. 날짜나 금액이 없어도 항목 등록은 허용한다. 대신 그 값이 필요한 D-day, 알림, 예상 지출에는 `계산할 수 없음: 다음 결제일 미확인`처럼 이유를 표시한다.

### 5.2 이미지 업로드로 등록 보조

지원하는 이미지 예시는 다음과 같다.

- 서비스 계정·멤버십 정보 화면
- 구독 관리·요금제 화면
- 다음 결제일·갱신일 안내 화면
- 결제 내역·영수증·안내 메시지
- 기프티콘·쿠폰·상품권 이미지
- 멤버십·보증기간 안내 이미지

처리 흐름은 다음과 같다.

1. 브라우저에서 이미지 미리보기를 보여준다.
2. 사용자는 분석 전에 필요한 영역을 자르거나 이메일·전화번호 등을 직접 가릴 수 있다.
3. 외부 AI로 전송될 분석용 이미지와 원본 보관 여부를 확인한다.
4. 분석용 이미지를 비공개 임시 공간에 올리고 OpenAI 이미지 이해 기능으로 분석한다.
5. 허용된 필드만 입력 폼 초안에 채운다.
6. 원본 또는 분석용 이미지와 초안을 나란히 보여준다.
7. 사용자가 누락값을 입력하고 오류를 수정한 뒤 저장한다.
8. 저장 성공 후 선택한 원본 보관 정책과 임시 파일 삭제 정책을 적용한다.

OpenAI 공식 문서는 Responses API가 이미지 입력 분석을 지원한다고 설명한다. 이미지 입력은 토큰으로 계산되어 비용이 발생하므로 이미지 크기·상세도·재시도를 기록하고 중복 분석을 막는다. [OpenAI 이미지 입력 문서](https://developers.openai.com/api/docs/guides/images-vision)

### 5.3 추출 규칙

- 이미지에 보이는 정보만 후보로 만든다.
- 필드마다 원문 근거, 출처 이미지, 정밀도, 사용자 확인 여부를 기록한다.
- 정확한 가입일·금액·주기·다음 결제일이 보이지 않으면 비워 둔다.
- `2025년 1월`은 `2025-01`과 `연·월` 정밀도로 저장한다. 1월 1일로 바꾸지 않는다.
- `네이버 멤버십을 통해 청구`만 보이면 결제 관계 후보로 저장한다. 무료·할인·추가 요금 여부는 확정하지 않는다.
- 이메일·전화번호·주소·계정 ID는 별도 관리 필드와 추출 결과에 저장하지 않는다.
- 자동 마스킹을 보조 기능으로 도입하더라도 완전한 제거를 보장하지 않는다. MVP는 사용자가 직접 자르고 가린 결과를 전송 전에 확인하는 흐름을 기준으로 한다.

### 5.4 이미지 개인정보와 보관

`개인정보를 관리 필드로 저장하지 않음`과 `원본 이미지에 개인정보가 없음`은 다른 의미다.

- 원본에는 이메일·전화번호·주문번호·바코드가 남아 있을 수 있다.
- 사용자가 가리지 않은 이미지 전체를 분석용으로 보내면 화면에 보이는 개인정보도 OpenAI로 전송될 수 있다.
- 전송 직전에 외부 AI 전송 사실, 전송할 이미지 미리보기, 목적, 공식 데이터 처리 안내 링크를 보여준다.
- 사용자가 자르거나 가린 분석용 사본만 OpenAI로 보내고, 편집하지 않았다면 선택한 전체 이미지가 전송된다.
- 원본 보관을 선택하면 편집 전 원본을 Supabase 비공개 Storage에 별도로 저장할 수 있다. 이 원본은 OpenAI 전송본과 다를 수 있다.
- 구독 계정·결제 화면은 `확정 후 원본 삭제`를 기본 추천으로 두고, 기프티콘·상품권·보증 증빙은 `원본 보관`을 기본 추천으로 둔다. 사용자가 바꿀 수 있다.
- 등록 취소 시 임시 파일은 즉시 삭제 대상으로 표시한다.
- 분석 실패 또는 저장하지 않은 초안은 마지막 활동 후 24시간이 지나면 삭제한다. 재시도 중인 작업은 만료 시각을 연장하되 최대 보관 기간을 운영 설정으로 제한한다.
- 추출 초안은 항목 확정 후 필요한 필드 근거만 남기고 모델 원문 응답과 임시 분석 파일은 삭제한다.

OpenAI API에 보낸 데이터의 보관은 우리 Storage 삭제와 별개다. 공식 문서에 따르면 API 데이터는 명시적으로 공유하지 않는 한 모델 학습에 사용되지 않지만, 기본 악용 모니터링 로그는 최대 30일 보관될 수 있고 Responses API의 애플리케이션 상태도 설정에 따라 저장될 수 있다. 설계상 `store=false`를 사용하고 출시 전에 프로젝트의 데이터 제어 자격과 실제 설정을 확인한다. 승인된 Zero Data Retention 여부를 기본값처럼 가정하지 않는다. [OpenAI 데이터 제어 문서](https://developers.openai.com/api/docs/guides/your-data)

## 6. 날짜와 반복 규칙

### 6.1 서로 다른 날짜의 의미

| 날짜 | 의미 |
| --- | --- |
| 최초 가입일 | 처음 이용을 시작한 기록. 다음 결제일의 대체값이 아님 |
| 다음 결제일 | 다음 청구가 예상되는 날짜. 직접 입력 또는 이미지에서 확인한 값 우선 |
| 갱신일 | 계약이나 이용 기간이 새로 시작되는 날짜 |
| 해지 마감일 | 다음 결제·갱신을 피하기 위해 해지해야 하는 마지막 날짜 |
| 검토일 | 사용자가 유지 여부를 생각하기로 정한 날짜 |
| 만료일 | 쿠폰·포인트·권리를 사용할 수 있는 마지막 날짜 |
| 보장 종료일 | 보증·보장 서비스가 끝나는 날짜 |
| 알림 시점 | 위 날짜를 언제 알려줄지 정한 별도 값 |

최초 가입일만으로 다음 결제일을 확정하지 않는다. 결제 주기와 가입일을 이용해 계산할 수 있는 경우에도 `계산된 예상 날짜`로 제안하고 사용자가 확인해야 확정값이 된다. 사용자가 확인하기 전에는 예상 회차 생성과 지출 예측에 사용할 수 있지만 화면에 `예상` 표시를 유지한다.

### 6.2 날짜 정밀도

| 입력 | 저장 정밀도 | 허용되는 사용 |
| --- | --- | --- |
| 2025년 | 연 | 연도별 이력 |
| 2025년 1월 | 연·월 | 월별 이력 |
| 2025년 1월 15일 | 날짜 | D-day, 종일 일정, 날짜 기준 알림 |
| 2025년 1월 15일 14:00 | 날짜·시각 | 정확한 시각 기준 알림 |

정확한 날짜가 없더라도 항목은 저장한다. D-day·알림·예상 지출 카드에서는 계산하지 못한 이유와 필요한 추가 정보를 보여준다.

### 6.3 월말·윤년·시간대

- 매월 반복은 원래 기준일을 별도로 보관한다. `1월 31일 → 2월 말일 → 3월 31일`처럼 2월 보정 뒤에도 기준일 31일을 유지한다.
- 매년 2월 29일 반복은 기준 월·일을 2월 29일로 보관하고, 평년에는 2월 말일로 보정하며 윤년에는 다시 2월 29일을 사용한다. 보정된 발생일에는 표시를 붙인다.
- 날짜만 있는 기한은 사용자의 시간대에서 종일 값으로 다룬다. D-day는 사용자의 현지 달력 날짜 차이로 계산한다.
- 시각까지 있는 값은 UTC 시각과 원래 시간대를 함께 저장한다. 표시할 때 사용자의 현재 시간대로 변환한다.
- 사용자가 시간대를 바꾸면 종일 날짜는 같은 현지 날짜를 유지하고, 시각이 있는 순간은 같은 UTC 시점을 유지한다.
- 만료일의 종료 시각이 출처에 없으면 자정으로 단정하지 않는다. 알림용 기본 시각은 사용자가 설정하며, 실제 사용 가능 종료 시각은 `미확인`으로 표시한다.

## 7. 구독 상태와 사용자 계획

구독을 하나의 일직선 상태로 표현하지 않는다. 다음 세 축을 분리한다.

| 축 | 가능한 값 |
| --- | --- |
| 실제 이용 상태 | 체험 중, 이용 중, 일시 중지, 결제 문제 확인, 이용 종료, 확인 필요 |
| 자동 갱신 상태 | 켜짐, 꺼짐, 수동 갱신, 확인 필요 |
| 사용자 계획 | 계획 없음, 유지 예정, 해지 검토, 특정 날짜까지 해지 예정, 재가입 검토 |

별도 기록으로 `사용자가 확인한 해지 완료일`, `현재 이용 가능 종료일`, `상태 출처`를 둔다.

- 해지 예정이었다가 유지하기로 하면 사용자 계획만 `유지 예정`으로 되돌린다.
- 자동 갱신을 해제해도 남은 이용 기간에는 실제 이용 상태를 `이용 중`으로 유지하고 종료 예정일을 표시한다.
- 자동 갱신을 다시 켜면 갱신 상태와 미래 예상 회차를 다시 계산한다.
- 이용 종료 후 재가입하면 과거 기간을 덮지 않고 새 이용 기간을 만든다.
- 금융·앱스토어 연동이 없는 MVP에서는 결제 실패를 자동 탐지하지 않는다. 사용자가 입력하거나 결제 안내 이미지에서 확인한 경우에만 `결제 문제 확인`으로 기록하고, 문제 발생만으로 이용 종료를 확정하지 않는다.
- 출처가 오래됐거나 서로 충돌하면 `확인 필요`로 표시한다.

서비스가 실제 해지를 대신 실행하지 않는다. 해지 예정과 해지 완료는 사용자가 확인한 내용을 기록하는 기능이다.

## 8. 결합 구독과 중복 비용 방지

하나의 결제로 여러 서비스를 이용하거나, 상위 멤버십에 추가 요금을 내고 다른 서비스를 이용할 수 있다. 서비스 이용 항목과 비용 청구 항목을 분리한다.

| 결제 관계 | 의미 | 지출 반영 |
| --- | --- | --- |
| 직접 결제 | 해당 서비스를 단독으로 결제 | 해당 청구 항목의 금액 반영 |
| 포함 혜택 | 상위 구독 가격에 포함 | 하위 서비스는 `상위 비용에 포함`; 별도 합산하지 않음 |
| 연결된 추가 요금 | 상위 구독을 통해 별도 추가 요금 청구 | 확인된 추가 요금만 별도 합산 |
| 금액 미확인 연결 | 관계는 확인했으나 포함·추가 금액을 모름 | 합계에서 제외하고 확인 필요 표시 |

필수 필드는 이용 서비스, 청구 항목, 관계 유형, 연결된 상위 구독, 기본·추가 요금 구분, 지출에 반영할 금액, 출처·확인 상태다.

예를 들어 네이버 멤버십을 통해 넷플릭스를 이용한다면 넷플릭스는 이용 서비스, 네이버 멤버십은 연결된 상위 구독이 된다. 이미지에서 연결 관계만 보이고 추가 금액은 보이지 않으면 `금액 미확인 연결`로 저장한다. 무료 이용이나 특정 할인액을 확정하지 않는다.

하나의 등록 요금과 예상 청구액은 한 비용 귀속 항목에서만 합산한다. 포함 혜택의 하위 서비스 카드는 이용 현황에는 보이지만 지출 합계에서는 상위 구독과 중복 계산하지 않는다. 후속 거래 처리에서도 실제 결제 하나를 하나의 비용 귀속에 연결하는 원칙을 유지한다.

## 9. 예상 결제 일정과 지출 리포트

MVP는 실제 금융 거래를 확인하지 않는다. 사용자가 등록한 요금·결제 주기·날짜와 과거 가격 정보를 이용해 예상값을 계산한다.

### 9.1 예상 결제 회차

반복 구독은 확인된 또는 사용자가 승인한 다음 결제일을 기준으로 예상 회차를 만든다. 회차에는 예정일, 예상 금액, 통화, 가격 구간, 계산 근거와 상태를 저장한다.

| 회차 상태 | 의미 |
| --- | --- |
| 예정 | 미래에 청구될 것으로 예상되는 회차 |
| 날짜 미확인 | 금액이나 주기는 있으나 정확한 예정일을 모름 |
| 금액 미확인 | 예정일은 있으나 금액을 모름 |
| 지난 회차·결제 여부 미확인 | 예정일이 지났지만 실제 결제 여부를 확인할 수 없음 |
| 건너뜀 | 사용자가 무료 기간·결제 유예 등으로 청구되지 않았다고 기록 |
| 취소 | 해지·요금제 변경 등으로 더 이상 유효하지 않은 미래 회차 |

예정일이 지났다는 이유만으로 결제 완료나 실제 지출로 바꾸지 않는다. `지난 회차·결제 여부 미확인`으로 표시한다.

다음 회차는 원래 반복 기준일, 결제 주기, 적용 중인 가격 구간에서 생성한다. 월말 보정일을 다음 기준일로 사용하지 않는다.

### 9.2 MVP에서 보여줄 세 가지 금액

| 금액 | 계산 기준 | 표시 원칙 |
| --- | --- | --- |
| 예상 청구액 | 유효한 미래 예상 회차의 등록 요금 | 청구 예정 기간과 포함·제외 항목 표시 |
| 월 환산액 | 현재 반복 요금을 월 단위로 환산 | 실제 결제액이 아닌 비교 지표로 표시 |
| 추정 누적액 | 확인 가능한 이용 기간과 해당 기간에 적용된 과거 요금 정보 | 가정과 계산 구간을 표시하고 근거가 부족하면 계산하지 않음 |

추정 누적액은 현재 가격을 과거 전체에 단순 적용하지 않는다. 가격 이력이 없는 기간, 일시 중지 여부가 불명확한 기간, 금액 미확인 결합 구독은 제외하고 제외 이유를 보여준다.

금액 미확인 항목을 0원이나 무료로 취급하지 않는다. 합계에는 계산된 금액과 제외된 항목 수를 함께 표시한다.

> 확인된 월 환산액 35,000원 · 금액 미확인 구독 2개 제외

계산 가능한 항목이 하나도 없으면 `0원` 대신 `계산할 정보 없음`을 표시한다.

### 9.3 가격·상태 변경의 영향

- 가격 변경은 적용 시작일이 있는 새 가격 구간을 만든다.
- 미래 예상 회차는 새 가격과 적용일에 맞게 갱신한다.
- 이미 지난 추정 구간은 당시 가격 이력이 있을 때만 다시 계산하며 변경된 근거를 남긴다.
- 자동 갱신 해제·사용자가 확인한 해지 완료 시 이용 가능 종료일 이후의 미래 회차를 취소한다.
- 이용 가능 종료일이 불명확하면 미래 회차를 자동 취소하지 않고 `종료일 확인 필요`로 표시한다.
- 다른 통화는 원통화로 보존한다. 환율 출처와 기준일이 정해지기 전에는 하나의 원화 합계로 단정하지 않는다.

### 9.4 후속 기능: 실제 결제·환불 거래 처리

후속 기능에서는 예상 회차와 실제 금융 기록을 대사한다. MVP 필수 구현과 분리하되 다음 설계를 보존한다.

- 실제 결제 거래의 별도 등록·관리
- 영수증과 예상 결제 회차의 후보 매칭 및 사용자 확인
- 하나의 회차에 대한 부분·분할 결제
- 환불 거래와 원 결제 연결
- 하나의 결제에 대한 부분·복수 환불과 환불 귀속 집계
- 예상액과 실제액의 차이 보존
- 영수증 해시, 거래일, 금액, 통화, 서비스, 결제 경로에 따른 중복 후보 확인
- 실제 결제가 연결된 회차에서 예상액과 실제액을 중복 합산하지 않는 규칙

후속 기능에서도 서비스가 결제·취소·환불을 실행하지 않는다. 사용자가 제공한 거래 기록을 저장하고 연결하는 기능이다.

## 10. 캘린더·알림·자동 삭제

### 10.1 일정과 알림

항목의 날짜에서 결제, 갱신, 해지 마감, 검토, 만료, 보장 종료 이벤트를 만든다. 이벤트와 알림 규칙을 분리해 하나의 날짜에 여러 알림을 설정할 수 있게 한다.

| 채널 | 역할 |
| --- | --- |
| 앱 안 알림 | 계정의 알림함에 저장. 외부 발송 실패와 관계없이 확인 가능 |
| Web Push | 권한을 허용한 기기에 발송. 기기·브라우저·네트워크에 따라 지연 또는 실패 가능 |
| Google Calendar 알림 | 내보낸 Google 일정의 설정에 따라 Google이 발송. 앱 알림과 별개 |

Web Push는 HTTPS와 서비스 워커가 필요하다. iOS·iPadOS는 지원 버전에서 홈 화면에 추가한 웹 앱에 Web Push를 제공하지만, 사용자의 알림 권한 허용이 필요하다. [MDN Service Worker 문서](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API), [WebKit Web Push 문서](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

### 10.2 정기 작업

정기 작업은 Supabase Cron이 인증된 FastAPI 내부 작업 엔드포인트를 호출하는 구성을 기본안으로 한다. Supabase Cron은 정기 SQL·함수·HTTP 작업을 지원하지만 현재 공식 기능 페이지에서 Beta로 표시되므로, 출시 전 운영 안정성을 확인하고 필요하면 별도 작업 실행기로 교체할 수 있게 작업 로직을 FastAPI에 둔다. [Supabase Cron 사용 문서](https://supabase.com/docs/guides/cron/quickstart), [Supabase Cron 기능 상태](https://supabase.com/features/supabase-cron)

| 작업 | 기본 실행 주기 | 처리 내용 |
| --- | --- | --- |
| 알림 예약·발송 | 5분마다 | 발송 시각이 지난 미발송 알림을 잠금 후 처리 |
| 회차 상태 점검 | 매시간 | 지난 예정 회차를 확인 대기로 변경, 미래 회차 보충 |
| 이미지 삭제 | 매시간 | 휴지통 이동 후 30일이 지난 파일 삭제 |
| 임시 파일 정리 | 매시간 | 취소·실패·24시간 방치 초안 정리 |
| 소식·해지 자료 갱신 | 서비스별 주기 | 만료된 공통 자료만 재검색 |

`사용자 + 이벤트 + 채널 + 예정 시각`의 고유 키와 발송 로그로 동일 작업의 중복 실행을 막는다. 다만 외부 Push 제공자에 요청을 보낸 뒤 응답이 끊기면 실제 기기 도착 여부를 확정할 수 없다. 발송 상태를 `대기`, `처리 중`, `요청 성공`, `실패`, `결과 불명`으로 구분하고, 결과 불명 재시도는 횟수와 간격을 제한한다. 따라서 서버 작업의 중복은 줄이되 외부 기기에 반드시 정확히 한 번 도착한다고 보장하지 않는다.

날짜 수정·기간 연장·구독 종료·자동 갱신 변경 시 미래 이벤트와 미발송 알림을 취소하고 새 값으로 다시 만든다. 이미 보낸 알림 이력은 지우지 않는다.

### 10.3 이미지 사용 완료와 삭제

쿠폰 사용 상태와 이미지 보관 상태를 분리한다.

| 구분 | 상태 |
| --- | --- |
| 사용 상태 | 미사용, 일부 사용, 사용 완료, 만료 |
| 이미지 상태 | 임시, 보관, 휴지통, 삭제 중, 영구 삭제, 삭제 실패 |

- `사용 완료`를 누르면 사용일을 기록하고 기프티콘·쿠폰·상품권 이미지를 휴지통으로 이동한다.
- 휴지통 이동 시각으로부터 30일 뒤는 `삭제 대상 시각`이다. 실제 파일 삭제는 그 시각 이후 처음 실행되는 정기 작업에서 처리하므로 몇 분 이상 늦어질 수 있다.
- 이미지를 복원하면 삭제 예약을 취소한다. 사용 완료 상태는 자동으로 취소하지 않는다.
- 사용 완료를 되돌리려면 사용 상태를 별도로 수정한다.
- 즉시 삭제는 확인 후 삭제 작업을 예약하며 성공 전까지 `삭제 중`으로 표시한다.
- 파일 삭제 실패 시 지수형 간격으로 재시도하고, 최대 횟수 이후 `삭제 실패`와 운영 확인 필요 상태를 남긴다.
- 복원과 삭제가 동시에 요청되면 첨부파일의 상태 버전과 잠금을 확인해 하나만 성공시킨다. 삭제 작업이 파일을 지우기 전에 복원이 확정되면 삭제를 중단한다. 이미 영구 삭제가 완료됐다면 복원은 실패로 표시하고 관리 이력만 유지한다.
- 이미지 삭제 후에도 사용자가 확정한 구독·사용 이력은 남긴다. 원본 이미지, 바코드, 임시 추출 응답은 삭제한다.
- 관리 항목 삭제 시 미래 예상 회차·이벤트·알림을 취소하고, 연결 이미지도 함께 휴지통으로 보낼지 확인한다. 항목 삭제와 이미지 영구 삭제는 별도 상태로 기록해 파일 삭제 실패가 항목 삭제 성공으로 숨겨지지 않게 한다.

## 11. Google Calendar 연동

MVP는 선택적인 단방향 내보내기를 제공한다. subscribe-manager를 원본으로 하고 사용자가 고른 이벤트만 Google Calendar에 만든다.

### 사용자 화면과 흐름

1. 설정에서 Google Calendar 연결을 선택한다.
2. 요청할 권한과 전송할 데이터 범위를 보여준다.
3. 전용 보조 캘린더 생성 또는 기존 캘린더 선택을 제공한다.
4. 결제·만료·검토 등 내보낼 이벤트 종류를 선택한다.
5. 동기화 결과, 마지막 성공 시각, 재인증 필요 여부를 보여준다.

앱 이벤트 ID와 Google 캘린더·이벤트 ID를 매핑하고, 앱 전용 ID와 비공개 확장 속성을 사용해 재시도 시 중복 생성을 막는다. 날짜 수정은 매핑된 이벤트를 수정하고, 항목 삭제·내보내기 해제는 매핑된 이벤트만 삭제한다.

Google Calendar에서 사용자가 직접 바꾼 값은 MVP에서 앱으로 가져오지 않는다. 다음 내보내기 때 앱 값으로 되돌아갈 수 있음을 표시한다. 연결 해제 때 `내보낸 일정 삭제`와 `Google에 남기기`를 선택하게 한다.

OAuth 토큰 만료·권한 철회는 `재연결 필요`로 표시한다. Google API 실패는 지수형 재시도를 사용하고 앱 내부 일정과 알림에는 영향을 주지 않는다.

Google 공식 문서는 최소 권한 사용을 권장하고, 앱이 만든 보조 캘린더를 관리하는 범위를 제공한다. 공개 앱은 사용하는 권한에 따라 OAuth 검증이 필요할 수 있으므로 출시 조건으로 관리한다. [Google Calendar 권한 문서](https://developers.google.com/workspace/calendar/api/auth), [이벤트 생성과 ID 문서](https://developers.google.com/workspace/calendar/api/guides/create-events), [확장 속성 문서](https://developers.google.com/workspace/calendar/api/guides/extended-properties)

## 12. 구독 해지 방법 안내

### 사용자가 보는 화면

- 현재 등록된 결제 경로
- 경로별 해지 메뉴 순서
- 검증된 구독 관리·해지 페이지 링크
- 해지 전에 확인할 조건
- 해지 후 이용 가능한 기간
- 공식 출처, 발표·수정일, 마지막 확인일
- 확인되지 않은 항목과 재확인 필요 표시
- `해지 검토`, `해지 예정`, `사용자가 확인한 해지 완료` 기록 버튼

### 입력과 출력

입력은 서비스, 국가, 요금제, 가입·결제 경로다. 출력은 해당 조합에 맞는 공식 절차와 근거다. 결제 경로를 모르면 여러 절차를 섞지 않고 먼저 확인 질문을 보여준다.

### 수집·저장·갱신

- 서비스 공식 도움말과 정책, Apple App Store·Google Play·통신사 등 실제 결제 경로의 공식 문서를 우선 검색한다.
- `(서비스, 국가, 결제 경로, 요금제)` 단위로 공통 안내를 저장한다.
- 단계별 설명과 각 주장에 사용한 출처 URL을 연결한다.
- 문서 접근 성공 시각, 마지막 검토 시각, 재확인 예정일을 저장한다.
- 일정 기간이 지나거나 사용자가 오류를 신고하면 다시 확인한다.

### 주요 규칙

- LLM이 URL을 조합하거나 추측해 만들지 못하게 한다. 검색 결과에서 실제로 연 공식 URL만 저장한다.
- 직접 해지 링크를 확인하지 못하면 공식 도움말과 메뉴 이동 경로만 제공한다.
- 국가·결제 경로가 다르면 같은 서비스의 안내를 합치지 않는다.
- 환불·종료 시점이 공식 자료에 없으면 `확인 필요`로 둔다.
- 서비스 안의 해지 상태는 사용자가 확인한 기록이며 실제 해지 실행이 아니다.

### 실패·정보 부족 표시

`공식 자료 접근 실패`, `결제 경로 미확인`, `절차는 확인했으나 직접 링크 없음`, `조건 확인 필요`, `오래된 안내`를 구분한다. 마지막으로 확인한 공식 홈페이지 링크와 사용자가 직접 확인할 경로를 제공한다.

### 완료 기준

- 지원 카탈로그의 각 서비스에서 최소 한 개 결제 경로의 공식 출처가 연결된다.
- 잘못된 결제 경로의 절차가 섞이지 않는다.
- 저장된 모든 외부 링크가 마지막 확인 시점에 열렸다는 기록이 있다.
- 출처가 없는 해지 단계와 URL이 사용자 화면에 나타나지 않는다.

## 13. 서비스별 최신 소식

최신 소식은 OTT에 한정하지 않는다.

| 서비스 유형 | 수집할 소식 예시 |
| --- | --- |
| OTT | 주요 공개 예정작, 새 작품, 제공 종료 예정작 |
| AI 도구 | 새 모델·기능, 이용 한도, 지원 요금제 변경 |
| 디자인 도구 | 편집·협업·생성형 AI 기능 변경 |
| 게임 구독 | 추가·제공 종료 게임, 요금·혜택 변경 |
| 쇼핑·배달 멤버십 | 가격, 적립·배송·쿠폰 조건 변경 |
| 음악·독서·강의 | 관심 콘텐츠, 이용권·기능 변경 |
| 가전 구독 | 상품, 관리 서비스, 혜택·조건 변경 |

### 사용자가 보는 화면

서비스별 피드와 통합 피드를 제공한다. 카드에는 제목, 핵심 변경, 내 요금제·국가와의 관련성, 발표일, 실제 적용일, 출처, 마지막 확인 시각, 확인 필요 항목을 표시한다.

### 입력과 출력

입력은 사용자의 구독 서비스·요금제·국가·결제 경로와 `써보고 싶어요`, `이 혜택에 관심 있어요` 같은 반응이다. 출력은 공통 소식 중 사용자에게 관련 있는 항목과 관련성의 이유다.

### 수집·저장·갱신

1. 서비스별 수집 작업이 웹 검색 가능한 LLM으로 공식 발표와 신뢰할 수 있는 원문을 찾는다.
2. URL을 실제로 열어 제목·날짜·대상 조건을 확인한다.
3. 서비스, 소식 유형, 출처 URL, 발표 주체, 적용일, 내용 유사도로 중복을 병합한다.
4. 공통 소식과 출처를 한 번 저장한다.
5. 사용자별 구독·요금제·국가·관심사와 비교해 관련성을 별도로 저장한다.
6. 변경 가능성이 큰 가격·혜택·제공 종료 정보는 더 짧은 주기로 재확인한다.

OpenAI 웹 검색은 최신 정보와 인용 URL을 반환할 수 있으며 사용자 화면에는 인용을 눈에 띄고 클릭 가능하게 표시해야 한다. 검색 호출과 검색 문맥 토큰에는 비용이 있으므로 서비스별 공통 수집과 캐시가 필요하다. [OpenAI 웹 검색 문서](https://developers.openai.com/api/docs/guides/tools-web-search), [OpenAI API 가격 문서](https://developers.openai.com/api/docs/pricing)

### 주요 규칙

- 같은 소식을 사용자마다 다시 검색하지 않는다.
- `새 모델 발표`와 `내 요금제에서 이용 가능`을 별도 사실로 검증한다.
- 발표일과 실제 적용일을 구분한다.
- 기존 가입자·신규 가입자, 국가, 요금제 조건을 분리한다.
- 검색 결과 원문 전체를 저장하지 않고 요약과 출처·근거 구간을 저장한다.
- 소식이 적거나 없다는 이유만으로 해지를 추천하지 않는다.
- 검색으로 확인한 일부 공개 예정작·신규 작품을 해당 OTT의 전체 편성 목록처럼 표현하지 않는다.

### 실패·정보 부족 표시

| 상태 | 사용자 표시 |
| --- | --- |
| 검색 호출 실패 | `소식을 확인하지 못함`, 실패 시각과 재시도 예정 |
| 검색 성공, 새 항목 없음 | `확인한 범위에서 새 소식 없음`, 범위와 확인 시각 |
| 소식 확인, 적용 조건 불명 | 소식은 표시하고 `내 요금제 적용 여부 확인 필요` |
| 출처 접근 불가 | 제목만으로 내용을 만들지 않고 `원문 확인 실패` |

### 완료 기준

- 모든 지원 서비스에 수집 상태와 마지막 시도가 표시된다.
- 공통 소식 하나를 여러 사용자에게 재사용한다.
- 사용자별 관련성에는 근거 또는 `확인 필요`가 있다.
- 모든 사실 카드에 클릭 가능한 출처와 확인 시각이 있다.
- 검색 실패와 새 소식 없음이 서로 다른 상태로 보인다.

## 14. 후속 기능: OTT 취향·조합 추천

MVP에는 OTT를 포함한 서비스별 최신 소식만 제공한다. 아래 취향·조합 추천은 후속 기능으로 보존한다.

### 사용자가 보는 화면

- 처음 취향 설문: 선호·비선호 장르, 좋아하는 작품, 월 예산, 현재 OTT
- 작품 카드의 `보고 싶어요`, `봤어요`, 관심 취소
- OTT 조합 선택 토글
- 선택 조합에서 제공이 확인된 관심 작품
- 제공처가 확인되지 않은 관심 작품
- 조합의 다음 청구 주기 예상 비용과 현재 구성과의 차이
- 추천 점수의 구성과 추천 이유

### 입력과 출력

입력은 설문, 관심 작품, 사용자가 직접 기록한 이용 상황, 현재 구독·요금제·갱신일, 국내 작품 제공 근거다. 출력은 몇 개의 추천 조합, 각 조합의 확인된 작품 커버리지, 중복 제거 결과, 미래 예상 비용 차이와 근거다.

### 데이터 수집·저장·갱신

- 작품은 고유 작품 ID로 관리하고 제목 번역·시즌을 별도 식별한다.
- 제공 정보는 작품, OTT, 국가, 제공 시작·종료일, 상태, 출처, 확인 시각을 저장한다.
- 주요 공개 예정작 검색 결과와 전체 편성표를 구분한다.
- 요금제 가격과 제공 작품은 서로 다른 갱신 주기를 갖는다.
- 사용자의 관심 반응과 설문은 사용자별 비공개 데이터로 저장한다.

### 추천 규칙

1. 국내 제공이 확인된 관심 작품만 `볼 수 있음`으로 계산한다.
2. 여러 OTT에 있는 같은 작품은 합집합에서 한 번만 센다.
3. 검색 결과에 없으면 `볼 수 없음`이 아니라 `제공처 미확인`으로 둔다.
4. 장르·좋아하는 작품·관심 작품·사용자가 입력한 이용 상황에 설명 가능한 가중치를 적용한다.
5. 현재 활성 요금제와 다음 갱신일을 이용해 다음 청구 주기의 예상 비용을 계산한다.
6. 비용 차이는 이미 결제한 금액의 환불이 아니라 미래 예상 지출 차이로 표시한다.
7. 자동 갱신 해제와 해지 마감일을 고려해 실제로 변경 가능한 시점을 보여준다.
8. 소식이나 관심 표시가 적다는 이유만으로 해지를 추천하지 않는다.

### 실패·정보 부족 표시

- 작품 제공 정보가 오래되면 `재확인 필요`로 표시한다.
- 요금제가 없으면 비용 비교에서 제외하고 필요한 값을 입력하도록 한다.
- 제공 정보가 부족한 조합은 정확한 최적 조합이라고 표현하지 않는다.
- 일반 공개일만 확인된 작품은 국내 OTT 공개 예정으로 확정하지 않는다.

### 완료 기준

- OTT 토글을 바꾸면 관심 작품 합집합과 예상 비용이 함께 갱신된다.
- 같은 작품이 중복 계산되지 않는다.
- 확인된 제공, 미확인 제공, 제공 종료가 구분된다.
- 모든 추천에 점수 구성과 비용 기준일이 표시된다.
- 갱신일이 없는 경우 절약 가능 시점을 단정하지 않는다.

## 15. 지출 리포트와 인터랙티브 구 시각화

### 사용자가 보는 화면

상단에는 이번 달 예상 청구액, 추정 누적액, 현재 구독 월 환산액을 별도 카드로 보여준다. 각 카드에는 계산 근거, 제외된 금액 미확인 항목 수, 기준일을 표시한다. 그 아래에 예상 청구 추세, 서비스별 표, 예상 회차 목록과 인터랙티브 구 화면을 둔다.

### 구 시각화 입력과 출력

구 하나는 기본적으로 하나의 이용 서비스를 뜻한다. 결합 구독은 상위 청구 관계를 선이나 그룹으로 표시하며 포함 혜택 금액을 다시 합산하지 않는다.

사용자는 구 크기의 기준을 전환할 수 있다.

- 월 환산액
- 추정 누적액
- 구독한 개월 수

구를 선택하면 요금제, 결제 관계, 다음 결제일, 예상 청구액, 계산 가능한 추정 누적액, 가입·종료·재가입 이력을 보여준다. 활성·종료·확인 필요 상태를 색과 텍스트로 구분한다.

### 데이터 갱신과 규칙

- 요금·예상 회차·상태·결합 관계가 변경되면 리포트 집계 스냅샷을 무효화한다.
- 극단값으로 작은 서비스가 사라지지 않도록 크기 범위를 제한하고 실제 숫자를 툴팁과 표에 표시한다.
- 선택한 크기 기준과 단위를 항상 표시한다.
- 실제 사용 빈도는 별도 기록이나 공식 연동 없이는 표시하지 않는다.
- 움직임을 끈 사용자에게 정적인 배치와 표 보기를 제공한다.

참고한 OriginKit Rubber Spheres 페이지는 2026-11-02 현재 이 환경에서 공식 페이지 내용과 사용 조건을 확인하지 못했다. 따라서 MVP의 기능 요구사항은 특정 외부 컴포넌트에 의존하지 않는다. 도입 전 접근 권한, 라이선스, React 호환성, 모바일 성능, 접근성을 확인하고, 확인되지 않으면 동일한 정보 구조를 가진 자체 시각화로 제공한다.

### 실패·정보 부족 표시

- 금액 미확인 서비스는 동일 크기로 꾸미지 않고 `금액 미확인` 그룹에 둔다.
- 통화가 다르고 환율 기준이 없으면 통합 크기 비교를 제한한다.
- 시각화 렌더링 실패 시 같은 필터가 적용된 표와 그래프를 유지한다.

### 완료 기준

- 세 가지 크기 기준 전환 결과가 표의 숫자와 일치한다.
- 포함 혜택이 상위 구독과 중복 집계되지 않는다.
- 키보드로 구를 선택하고 상세를 열 수 있다.
- 동작 줄이기와 표 대체 보기가 작동한다.

## 16. 핵심 데이터 구조

기술 스택은 React, FastAPI, Supabase를 유지한다. React는 사용자 화면, FastAPI는 권한 검증·업무 규칙·OpenAI 및 외부 API 호출·정기 작업, Supabase는 Auth·Postgres·비공개 Storage를 담당한다.

### 16.1 주요 테이블과 관계

| 테이블 | 역할과 주요 필드 |
| --- | --- |
| `profiles`, `preferences` | 사용자, 시간대, 통화, 알림 기본값, 개인정보 안내 동의 버전 |
| `services`, `plans`, `features` | 공통 서비스 카탈로그, 요금제, 실제 서비스 아래의 모델·기능 |
| `items` | 사용자 관리 항목, 유형, 제목, 실제 이용 상태, 자동 갱신 상태, 사용자 계획, 삭제 상태·시각 |

| `calendar_connections`, `calendar_event_links` | OAuth 연결, 앱 이벤트와 Google 이벤트 매핑 |
| `cancel_guides`, `cancel_guide_sources` | 경로별 해지 절차, 공식 출처, 검증·만료 상태 |
| `news_items`, `news_sources` | 공통 소식, 발표·적용일, 조건, 출처, 확인 시각 |

| `titles`, `title_availability` | 후속 OTT 추천용 작품과 국가·OTT별 제공 상태·기간·출처 |
| `user_tastes`, `title_reactions` | 후속 OTT 추천용 취향 설문, 보고 싶어요·봤어요 |
| `search_jobs`, `llm_usage` | 검색·LLM 작업의 입력 키, 캐시, 상태, 토큰·호출 비용 |
| `audit_events` | 상태·가격·관계·이미지·결제 연결 변경 이력 |

주요 관계는 다음과 같다.

- 사용자 한 명은 여러 관리 항목을 가진다.
- 관리 항목 하나는 여러 이용 기간·가격 구간·날짜·결제 회차를 가진다.
- MVP의 예상 회차에는 실제 결제 여부를 자동 기록하지 않는다.
- 후속 거래 처리에서는 실제 결제 하나를 원칙적으로 하나의 예상 회차에 연결하고, 부분·분할 결제와 복수 환불을 별도 연결 테이블로 확장한다.
- 결합 구독은 하위 이용 항목에서 상위 비용 귀속 항목을 가리킨다.
- 공통 소식·해지 안내·작품 제공 정보는 사용자 데이터와 분리하고 사용자별 관련성만 별도로 저장한다.

`payment_transactions`와 실제 거래-회차 연결, `titles`, `title_availability`, `user_tastes`, `title_reactions`는 후속 기능 테이블이다. MVP 마이그레이션의 필수 대상에서 제외하되 이름 충돌을 피할 수 있도록 관계만 예약한다.

### 16.2 사용자 데이터 접근 제한

- 모든 사용자 소유 테이블은 `user_id`를 가지며 Supabase RLS로 본인 행만 조회·수정하게 한다.
- FastAPI도 토큰의 사용자 ID와 요청 자원의 소유자를 다시 확인한다.
- Storage는 비공개 버킷과 사용자별 경로를 사용하고 `storage.objects` RLS를 적용한다.
- 원본 보기는 짧은 만료 시간을 가진 서명 URL 또는 인증된 다운로드만 허용한다.
- 관리자용 비밀 키는 서버에서만 사용하고 브라우저에 전달하지 않는다.
- 공통 카탈로그·소식은 읽기 가능 범위를 별도 정책으로 두고 사용자 이미지·반응과 결합해 공개하지 않는다.

Supabase 공식 문서는 비공개 버킷 다운로드에 인증 또는 서명 URL이 필요하며 Storage 접근에 RLS를 적용할 수 있다고 설명한다. [Supabase Storage 문서](https://supabase.com/docs/guides/storage/buckets/fundamentals), [Storage 접근 제어 문서](https://supabase.com/docs/guides/storage/security/access-control), [사용자 데이터 RLS 문서](https://supabase.com/docs/guides/auth/managing-user-data)

## 17. 주요 API 계약

아래 경로는 구현 전에 합의할 논리 계약이다. 응답은 성공 데이터와 함께 `source`, `confirmation_status`, `missing_fields`, `warnings`를 필요한 곳에 포함한다.

### 17.1 MVP API

| 메서드·경로 | 입력 | 출력 |
| --- | --- | --- |
| `POST /api/v1/items` | 유형별 입력 폼, 날짜·금액·관계 | 생성된 항목, 계산 제한과 누락 필드 |
| `GET /api/v1/items` | 필터·정렬·페이지 | 사용자 항목 목록과 다음 이벤트 |
| `GET /api/v1/items/{item_id}` | 항목 ID | 상세, 이력, 결제 구조, 이미지 메타데이터 |
| `PATCH /api/v1/items/{item_id}` | 수정 필드와 변경 이유 | 새 상태와 재계산된 미래 이벤트 |
| `DELETE /api/v1/items/{item_id}` | 항목과 연결 이미지 처리 선택 | 삭제 결과, 취소된 미래 일정·알림, 이미지 삭제 상태 |
| `POST /api/v1/extraction-drafts` | 업로드된 분석 이미지 ID, 관리 유형 | 추출 초안, 근거, 정밀도, 누락값, 만료 시각 |
| `POST /api/v1/extraction-drafts/{draft_id}/confirm` | 사용자가 수정·확정한 필드, 원본 보관 선택 | 생성 항목과 파일 정리 결과 |
| `POST /api/v1/attachments/{id}/trash` | 이미지 ID | 휴지통 이동 시각과 자동 삭제 예정일 |
| `POST /api/v1/attachments/{id}/restore` | 이미지 ID | 보관 상태와 삭제 예약 취소 결과 |
| `DELETE /api/v1/attachments/{id}` | 즉시 삭제 확인 | 삭제 작업 상태 |
| `GET /api/v1/billing-occurrences` | 기간·상태·항목 | 예상·정보 미확인·지난 미확인·취소 회차 |
| `GET /api/v1/reports/spending` | 기간·통화·예상/추정 선택 | 예상 청구액·월 환산액·추정 누적액, 근거와 제외 항목 |
| `GET /api/v1/reports/spheres` | 크기 기준·필터 | 구 노드, 결합 관계, 표 대체 데이터 |
| `GET /api/v1/calendar/events` | 기간·이벤트 유형 | 내부 캘린더 이벤트 |
| `POST /api/v1/reminder-rules` | 이벤트, 상대 시점, 채널 | 예약된 알림과 제한 사유 |
| `POST /api/v1/integrations/google-calendar/connect` | 연결 옵션 | OAuth 시작 정보 |
| `POST /api/v1/integrations/google-calendar/sync` | 선택 이벤트·종류 | 생성·수정·삭제·실패 결과 |
| `DELETE /api/v1/integrations/google-calendar` | 일정 삭제 또는 유지 선택 | 연결 해제 결과 |
| `GET /api/v1/items/{id}/cancel-guide` | 국가·결제 경로·요금제 | 공식 절차, 출처, 확인 상태 |
| `GET /api/v1/news` | 사용자 구독·관심 필터 | 관련 소식, 적용 판단, 출처 |
| `POST /api/v1/interests` | 서비스·기능·혜택 관심 반응 | 저장된 관심과 소식 정렬 갱신 상태 |

`GET /api/v1/billing-occurrences`는 `예정`, `날짜 미확인`, `금액 미확인`, `지난 회차·결제 여부 미확인`, `건너뜀`, `취소` 상태를 반환한다. MVP에는 실제 결제 연결 상태를 만들지 않는다.

| 메서드·경로 | 입력 | 출력 |

## 18. 요청부터 저장·집계·알림까지의 흐름

### 직접 등록

사용자 입력 → 인증·소유자 확인 → 필드 검증 → 항목·가격·날짜·결제 관계 저장 → 미래 회차 생성 → 내부 이벤트 생성 → 알림 예약 → 리포트 캐시 무효화 → 선택한 Google 일정 동기화

### 이미지 등록

사용자 이미지 선택 → 자르기·가리기와 외부 전송 안내 → 임시 업로드 → 이미지 해시 중복 검사 → OpenAI 분석 → 허용 필드만 초안 저장 → 사용자 검토·확정 → 항목 저장 → 원본 보관 정책 적용 → 임시 분석 자료 삭제 예약 → 회차·이벤트·알림 생성

### 후속 기능: 실제 결제·환불 등록

영수증 또는 직접 입력 → 중복 후보 검사 → 예상 회차 후보 표시 → 사용자 연결 확인 → 실제·부분·분할 결제 저장 → 환불은 원 결제와 귀속 금액 연결 → 예상액과 실제액 차이 보존 → 실제 거래 집계 갱신

### 날짜·상태 변경

사용자 수정 → 과거 이력 보존 → 미래 회차·이벤트·미발송 알림 취소 → 새 값으로 재생성 → Google 일정 갱신 → 리포트 캐시 무효화

### 소식·해지 정보

서비스별 공통 작업 키 생성 → 유효한 캐시 확인 → 웹 검색·공식 페이지 열기 → 출처 검증 → 공통 DB 저장 → 사용자별 관련성 계산 → 화면에 출처·확인 시각과 함께 표시

## 19. 검색·LLM 비용과 중복 호출 방지

- 이미지 분석은 파일 해시, 분석 스키마 버전, 모델 설정을 묶은 키로 같은 초안의 중복 호출을 막는다. 다른 사용자의 이미지를 결과 캐시로 공유하지 않는다.
- 소식과 해지 안내는 서비스·국가·경로·요금제·검색 목적·기간을 작업 키로 사용한다. 동시에 같은 요청이 들어오면 하나의 작업에 합류한다.
- 공통 정보에는 `확인 완료`, `새 정보 없음`, `실패`, `부분 확인`, `재확인 필요` 상태와 다음 검색 가능 시각을 저장한다.
- 사용자 화면 새로고침이 곧바로 새 LLM 호출을 만들지 않는다.
- 모델명과 검색 설정은 운영 설정으로 두며 문서에 특정 최신 모델을 고정하지 않는다.
- 호출마다 모델, 토큰, 이미지 크기·상세도, 검색 횟수, 지연 시간, 예상 비용을 기록한다.
- 사용자별·전체 일일 예산, 동시 작업 수, 재시도 횟수, 회로 차단 기준을 둔다.
- 공식 출처의 원문이 이미 유효하면 LLM 요약만 다시 만들지 않고 저장된 구조화 자료를 재사용한다.
- 가격은 변경될 수 있으므로 숫자를 제품 정의에 고정하지 않고 운영 시 [OpenAI 공식 가격 문서](https://developers.openai.com/api/docs/pricing)를 기준으로 예산을 갱신한다.

## 21. MVP 구현 순서

### 1단계: 데이터와 접근 제어

- Supabase Auth, 사용자별 RLS, 비공개 Storage
- 서비스·항목·날짜·가격·이용 기간·결제 관계 모델
- 감사 이력과 공통 카탈로그

완료 기준: 다른 사용자의 행과 이미지에 접근할 수 없고 직접 등록 데이터가 이력과 함께 보존된다.

### 2단계: 등록과 이미지 검토

- 유형별 입력 폼
- 이미지 자르기·가리기, 전송 안내, 분석, 초안 확인
- 부분 날짜와 원본 보관·임시 삭제 정책

완료 기준: 이미지에 없는 값과 불필요한 개인정보 필드가 저장되지 않고, 사용자가 확인한 값만 항목으로 확정된다.

### 3단계: 예상 회차·결합 구독·리포트

- 예상 회차와 정보 미확인 상태
- 가격 변경과 추정 누적액 계산 근거
- 결합 구독 비용 귀속
- 예상 청구·추정 누적·월 환산 리포트와 구 시각화

완료 기준: 금액 미확인 항목이 0원으로 계산되지 않고, 결합 구독 비용이 중복되지 않으며 표·그래프·구의 숫자가 일치한다.

### 4단계: 캘린더·알림·파일 수명주기

- 내부 캘린더, 앱 알림, Web Push
- 월말·윤년·시간대 규칙
- 30일 휴지통, 임시 파일 정리, 재시도
- Google Calendar 단방향 연동

완료 기준: 작업 재실행에도 중복 알림이 없고 날짜 수정·복원·종료가 예약 작업과 외부 일정을 일관되게 갱신한다.

### 5단계: 해지 안내와 최신 소식

- 공식 자료 수집·검증·공통 저장
- 결제 경로별 해지 안내
- 전 서비스 유형의 최신 소식과 사용자 관련성

완료 기준: 출처 없는 절차·URL·적용 조건이 표시되지 않고 검색 실패와 새 정보 없음이 구분된다.

### 6단계: 통합 검증과 출시 준비

- 기능 간 상태·집계·알림 회귀 검증
- 외부 권한·요금·약관·출처 재확인
- 접근성·모바일·성능·비용 한도 점검

완료 기준: 이 문서의 기능별 완료 기준과 아래 통합 시나리오를 모두 통과한다.

### 후속 기능 구현 순서

1. 실제 결제·부분·분할 결제와 예상 회차 대사
2. 원 결제에 연결된 부분·복수 환불과 귀속 집계
3. OTT 작품 제공 데이터와 취향·보고 싶어요 반응
4. OTT 조합 추천, 커버리지와 미래 예상 비용 차이 시뮬레이션

후속 구현은 MVP 예상 회차와 서비스 카탈로그를 재사용하되 MVP 출시의 필수 조건으로 삼지 않는다.

## 22. 통합 완료 시나리오

1. 날짜가 없는 구독도 등록되며 D-day·알림·예상 지출이 제한된 이유가 보인다.
2. 가입일과 주기로 계산한 다음 결제일은 예상값으로 제안되고 사용자 확인 전까지 확정되지 않는다.
3. 넷플릭스 화면의 `2025년 1월`이 1월 1일로 바뀌지 않고, 화면에 없는 금액·주기·다음 결제일은 비어 있다.
4. 분석 전 이메일을 가리지 않은 경우 외부 전송 가능성을 안내하고, 이메일을 관리 필드로 저장하지 않는다.
5. 예정일이 지난 미확인 회차는 결제 완료가 아니라 `지난 회차·결제 여부 미확인`으로 보인다.
6. 금액 미확인 항목은 0원으로 계산되지 않고 합계에서 제외된 수와 이유가 보인다.
7. 모든 금액이 미확인이면 합계가 0원이 아니라 `계산할 정보 없음`으로 보인다.
8. 네이버 멤버십과 연결된 넷플릭스 혜택이 같은 비용으로 두 번 합산되지 않는다.
9. 자동 갱신을 꺼도 이용 종료일까지 이용 중으로 보이며 다시 켜면 미래 예상 회차가 갱신된다.
10. 1월 31일 월간 반복은 2월 말일 뒤 3월 31일로 돌아온다.
11. 정기 작업 재실행으로 같은 알림 요청이 중복 처리되지 않으며 외부 전달 결과 불명 상태를 확인할 수 있다.
12. 쿠폰 이미지를 복원하면 삭제 예약만 취소되고 사용 완료 상태는 유지된다.
13. 복원과 삭제가 충돌하면 하나만 성공하고 이미 삭제된 파일을 복원됐다고 표시하지 않는다.
14. Google Calendar 연결이 만료돼도 내부 일정과 알림은 유지된다.
15. 해지 안내의 모든 단계와 URL에 공식 출처와 확인일이 있다.
16. 소식 검색 실패, 새 소식 없음, 요금제 적용 여부 미확인이 다르게 표시된다.
17. OTT 소식의 일부 검색 결과가 전체 편성 목록처럼 표시되지 않는다.
18. 구 시각화의 크기와 표의 예상·추정 숫자가 일치하고 결합 구독 비용이 중복되지 않는다.
