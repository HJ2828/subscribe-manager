# subscribe-manager MVP 개발 계획

작성일: 2026-11-02

기준 문서: `docs/PRD.md`, `docs/spec.md`

## 1. 계획의 목표

이 계획은 `spec.md`의 MVP 기능을 의존 관계에 맞춰 개발하는 순서를 정한다. 각 Phase는 앞 단계의 결과를 사용하며, 외부 서비스가 실패해도 구독·생활 기한의 기본 관리 기능은 계속 사용할 수 있게 한다.

개발 기간은 임의로 정하지 않는다. 각 Phase의 완료 기준을 통과한 뒤 다음 Phase로 넘어간다.

## 2. 전체 개발 순서

| Phase | 목표 | 주요 결과 |
| --- | --- | --- |
| 0 | 미정 정책과 외부 검증 준비 | 결정 기록, 검증 목록, 공통 완료 기준 |
| 1 | 프로젝트 기반과 사용자 데이터 보호 | React·FastAPI·Supabase 기본 구조, 사용자별 접근 제한 |
| 2 | 회원가입·로그인과 사용자 설정 | 이메일 인증, 비밀번호 재설정, 기본 설정, 탈퇴 시작 흐름 |
| 3 | 구독·생활 기한 직접 관리 | 유형별 입력 폼, 목록·상세·수정·삭제, 날짜·상태·통화 |
| 4 | 이미지 등록과 파일 수명주기 | 업로드, AI 추출 초안, 사용자 확인, 보관·휴지통·정리 |
| 5 | 예상 일정·홈·캘린더·알림 | 12개월 예상 회차, 통합 홈, 내부 캘린더, 앱 알림·Web Push |
| 6 | 결합 구독·지출 리포트·시각화 | 비용 중복 방지, 통화별 집계, 기간 차트와 버블·그래프·표 |
| 7 | 제거됨 | Google Calendar 연동은 구현·검증 대상에서 제외 |
| 8 | 해지 안내·최신 소식·운영 검수 | 지원 카탈로그, 공식 자료, 공통 수집, 공개 상태 관리 |
| 9 | 통합 검증과 MVP 출시 준비 | 전체 시나리오 검증, 외부 조건 확인, 운영 준비 |

## 3. 공통 진행 원칙

- 각 기능은 정상 처리뿐 아니라 입력 오류, 외부 실패, 권한 오류와 부분 실패를 함께 구현한다.
- 사용자 소유 데이터는 화면과 서버 양쪽에서 본인 여부를 확인한다.
- 날짜·금액·통화를 확인할 수 없으면 추측하지 않는다.
- 실제 결제·환불·구독 해지 기능은 만들지 않는다.
- 외부 연동은 내부 저장이 완료된 뒤 실행하고, 외부 실패가 성공한 내부 작업을 되돌리지 않게 한다.
- 외부 서비스 검증 전에는 기능을 `지원 완료`로 표시하지 않는다.
- 각 Phase가 끝날 때 `spec.md`의 확인 기준으로 기능을 검증하고 결과를 기록한다.

## Phase 0. 정책 결정과 외부 검증 준비

### 목표

개발 중 임의의 값이 들어가지 않도록 결정이 필요한 정책과 외부 검증 항목을 작업 순서에 연결한다. 모든 결정을 끝낼 때까지 개발을 멈추는 것이 아니라, 해당 값이 필요한 Phase 전까지 확정한다.

### 진행 단계

1. `spec.md`의 사용자 결정 정책 15개를 Phase별로 분류한다.
2. 결정된 값은 PRD와 spec에 동시에 반영하고 결정 날짜를 남긴다.
3. Supabase, Web Push, OpenAI와 초기 정보 지원 후보의 검증 목록을 만든다.
4. 외부 검증 결과에 `검증 전`, `검증 중`, `검증 완료`, `사용 불가` 상태를 사용한다.
5. 테스트에 사용할 계정·브라우저·시간대·통화·샘플 이미지를 준비한다. 실제 비밀값은 문서나 저장소에 넣지 않는다.

### Phase 전에 확정할 정책

| 결정 항목 | 늦어도 필요한 Phase |
| --- | --- |
| 이메일·비밀번호 길이와 조합 | Phase 2 |
| 유형별 식별 이름, 텍스트·금액·날짜·주기 범위 | Phase 3 |
| 항목 삭제·과거 이력·이미지·복구·결합 관계 처리 | Phase 3 |
| Web Push 재시도 횟수와 간격 | Phase 5 |
| 오늘 예정 회차의 남은 예정액 포함 여부 | Phase 6 |
| 삭제 실패의 운영 확인 전환 기준 | Phase 4와 Phase 9 |
| 운영 도구 형태, 운영자 권한, 중요 변경 공개 방식 | Phase 8 |
| `임박` 기준 | Phase 8 |

### 완료 기준

- 미정값마다 적용 Phase와 현재 상태가 정리되어 있다.
- 외부 검증 결과와 제품 정책을 구분할 수 있다.
- 아직 결정되지 않은 값이 구현 기본값으로 몰래 확정되지 않는다.

## Phase 1. 프로젝트 기반과 사용자별 접근 제한

**진행 상태:** 로컬 구현·검증 완료 / 외부 Supabase 프로젝트 적용·검증 대기

### 목표

모든 기능이 사용할 공통 구조와 사용자 데이터 보호 기준을 먼저 만든다.

### 진행 단계

1. React 사용자 화면, FastAPI 서버와 Supabase 프로젝트의 기본 연결 구조를 만든다.
2. 개발·시험·운영 환경의 설정을 분리하고 비밀값을 브라우저와 저장소에 노출하지 않는다.
3. 사용자 소유 데이터와 공통 데이터의 구분 원칙을 적용한다.
4. 사용자 데이터는 본인만 읽고 바꿀 수 있도록 접근 제한을 설정한다.
5. 이미지는 비공개 저장 공간과 사용자별 경로를 사용한다.
6. 오류 응답은 사용자에게 필요한 안내만 보여주고 비밀 설정이나 내부 정보는 노출하지 않는다.
7. 날짜 계산이 공통으로 사용할 사용자 시간대와 날짜 정밀도 표현을 준비한다.

### 검증 항목

- 로그인하지 않은 요청은 보호된 데이터를 볼 수 없다.
- 사용자 A가 사용자 B의 항목 ID나 이미지 경로를 알아도 접근할 수 없다.
- 관리자용 비밀 키가 브라우저 결과에 포함되지 않는다.
- 공통 소식·해지 안내 데이터와 사용자 개인 데이터가 섞이지 않는다.

### 완료 기준

본인 데이터만 접근할 수 있는 최소 구조가 검증되고, 이후 기능이 같은 접근 원칙을 재사용할 수 있다.

## Phase 2. 회원가입·로그인·설정·탈퇴 시작 흐름

### 목표

사용자가 안전하게 계정을 만들고 로그인하며 기본 환경을 설정할 수 있게 한다.

### 진행 단계

1. 이메일·비밀번호 회원가입 화면과 입력 검사를 만든다.
2. 이메일 인증 없이 가입 직후 로그인되는 흐름을 만든다.
3. 로그인·로그아웃과 세션 만료 처리를 만든다.
4. 비밀번호 재설정 요청과 새 비밀번호 저장 흐름을 만든다.
5. 기본 국가 대한민국, 통화 원화, 시간대 `Asia/Seoul`을 적용한다.
6. 국가·통화·시간대·알림 기본값 설정 화면을 만든다.
7. 탈퇴 확인 즉시 로그아웃하고 접근·알림 대상에서 제외하는 흐름을 만든다.
8. 실제 개인 자료 삭제는 뒤 Phase에서 파일·알림·관심 데이터가 추가될 때 함께 확장할 수 있게 준비한다.

### 선행 결정·검증

- 이메일·비밀번호 길이와 문자 조합 확정
- Supabase 비밀번호 재설정 메일 설정과 제한 검증
- 운영 주소와 이메일 링크 이동 경로 검증

### 검증 항목

- 정상 가입, 중복 이메일, 잘못된 이메일과 비밀번호를 확인한다.
- 가입 직후 보호 화면에 접근할 수 있다.
- 재설정 링크 정상·만료·재요청을 확인한다.
- 로그아웃 뒤 이전 사용자 정보가 남지 않는다.

### 완료 기준

`spec.md`의 회원가입, 로그인, 비밀번호 재설정과 기본 설정 확인 기준을 모두 통과한다.

## Phase 3. 구독·생활 기한 직접 등록과 관리

### 목표

외부 AI나 캘린더가 없어도 핵심 관리 기능을 사용할 수 있는 첫 번째 완전한 흐름을 만든다.

### 진행 단계

1. 반복 결제 구독, 기간제 구독·멤버십, 기프티콘, 쿠폰, 상품권, 포인트, 보증, 기타 결제 기한과 기타 기한의 입력 조건을 확정한다.
2. 관리 유형 선택 후 해당 유형의 입력란만 보이는 폼을 만든다.
3. 0원과 금액 미확인을 구분하고 금액 입력 시 실제 결제 통화를 함께 받는다.
4. 일자와 연·월 날짜를 구분하고, 확인된 정밀도를 그대로 저장한다.
5. 실제 이용 상태, 자동 갱신 상태와 사용자 계획을 별도로 관리한다.
6. 최초 가입일만으로 다음 결제일을 확정하지 않고 예상값은 사용자 확인을 받는다.
7. 목록의 검색·유형·카테고리·상태·날짜·지원 범위 필터와 이름·날짜·금액 정렬을 만든다.
8. 반복 결제 구독을 제외한 항목은 기한이 지나면 `기간 만료` 상태로 자동 변경한다.
9. 상세 조회, 수정과 삭제 확인 흐름을 만든다.
10. 삭제 시 과거 이력, 미래 작업, 첨부 이미지, Google 일정과 결합 관계의 영향을 보여줄 구조를 만든다.
11. 외부 정리가 아직 없는 단계에서도 내부 삭제 결과와 정리 상태를 분리해 표현한다.

### 날짜 검증

- 날짜가 없는 항목도 저장된다.
- `2025년 1월`이 1월 1일로 바뀌지 않는다.
- 1월 31일 월간 반복의 다음 기준은 2월 말일 뒤 3월 31일이다.
- 자동 갱신이 켜진 월간·연간 반복 결제는 다음 결제일이 지나면 사용자 시간대 기준 다음 회차로 이월되고 목록·상세·캘린더·알림에 같은 날짜가 반영된다.
- 윤년과 사용자 시간대가 적용된다.
- 자동 갱신 해제와 실제 이용 종료가 별도 상태로 보인다.
- 반복 결제 구독은 자동 만료 대상에서 제외하고, 나머지는 일자·월 정밀도에 맞춰 지난 기한을 `기간 만료`로 표시한다.

### 삭제 검증

- 삭제 확인 전에 영향을 받는 데이터가 표시된다.
- 내부 삭제 실패 시 항목을 사라진 것처럼 표시하지 않는다.
- 사용자 결정 전 과거 이력이나 첨부 이미지를 임의로 삭제하지 않는다.
- 결합 관계가 있는 항목의 미정 삭제 정책을 임의로 처리하지 않는다.

### 완료 기준

모든 관리 유형을 직접 등록·조회·수정·삭제할 수 있고, 날짜·금액이 없어도 제한 이유와 함께 관리할 수 있다.

## Phase 4. 이미지 등록과 파일 수명주기

### 목표

이미지에서 초안을 만들되 사용자가 확인한 값만 저장하고, 원본·임시·휴지통 파일의 수명주기를 안전하게 관리한다.

### 진행 단계

1. JPEG·PNG·WebP 선택, 미리보기, 자르기와 가리기 화면을 만든다.
2. 확장자뿐 아니라 실제 이미지 형식, 손상 여부와 10MB 제한을 검사한다.
3. 외부 AI 전송 범위, 개인정보 가능성과 원본 보관 선택을 분석 전에 보여준다.
4. `gpt-5.4-mini` 후보의 이미지 입력·구조화 결과를 샘플로 검증한다.
5. 이미지 분석의 사용자당 하루 10회·예상 US$0.20 제한과 사용 상태 안내를 적용한다.
6. 모델명과 분석 설정을 교체 가능한 운영 설정으로 분리한다.
7. 이미지에서 확인된 허용 필드, 근거, 날짜 정밀도와 누락값을 초안으로 만든다.
8. Phase 3 직접 등록·수정 화면의 우측 이미지 토글에서 원본과 폼을 함께 보여준다. 신규 등록만 AI 초안을 적용하고, 사용자가 수정·확정한 뒤 같은 저장 흐름으로 저장한다.
9. 이메일·전화번호·주소·계정 ID가 관리 필드로 저장되지 않게 한다.
10. 사용자당 총 100MB 사용량을 원본·분석용·임시·휴지통 파일로 계산한다.
11. 한도 초과 시 기존 파일을 지우지 않고 정리 안내를 보여준다.
12. 등록 취소 파일은 즉시, 방치 초안은 마지막 활동 후 24시간이 지나면 삭제 대상으로 처리한다.
13. 기프티콘 등의 사용 완료와 이미지 휴지통 상태를 분리한다.
14. 휴지통 이동 30일 후 삭제 대상, 복원, 즉시 삭제와 삭제 실패 재시도를 만든다.
15. 계정 탈퇴 시 이미지·초안 삭제 작업을 연결한다.

### 선행 검증

- OpenAI 프로젝트의 모델 접근, 이미지·구조화 결과 조합, 품질과 예상 비용
- Supabase 전체 Storage 용량·전송량·요금
- 삭제가 계속 실패할 때 운영 확인으로 전환할 기준

### 검증 항목

- 이미지에 없는 금액·날짜·주기·통화가 만들어지지 않는다.
- 사용자 확정 전에는 관리 항목이 생기지 않는다.
- 100MB 초과로 기존 파일이 자동 삭제되지 않는다.
- 이미지 복원은 사용 완료를 취소하지 않는다.
- 복원과 삭제 충돌에서는 하나만 성공한다.

### 완료 기준

업로드부터 사용자 확정, 보관·휴지통·정리까지 전체 흐름이 동작하고 실패 상태가 숨겨지지 않는다.

## Phase 5. 예상 일정·통합 홈·내부 캘린더·알림

### 목표

등록 데이터를 사용자가 실제로 놓치지 않도록 일정과 알림으로 연결한다.

### 진행 단계

1. 요금·주기·확인한 다음 결제일·자동 갱신 상태로 오늘부터 12개월의 예상 회차를 만든다.
2. 시간이 지나면 부족한 기간만 보충하고 같은 회차를 중복 생성하지 않는다.
3. 연간 구독의 다음 일정도 12개월 범위 안에 표시한다.
4. 예정일이 지나도 실제 결제 완료로 바꾸지 않고 `지난 회차·결제 여부 미확인`으로 둔다.
5. 통합 홈에 다음 30일 예정 결제액·결제 건수·혜택 만료 건수, 가까운 일정 최대 6개, 월간 미니 캘린더와 확인 필요 영역을 만든다.
6. 내부 캘린더의 월간·주간·목록 보기와 일정 종류 필터를 만든다.
7. 기본 3일 전·당일 오전 9시 앱 안 알림을 사용자 시간대로 예약한다.
8. 오후 10시~오전 8시 조용한 시간과 의미가 없어진 지연 알림 제외 규칙을 적용한다.
9. Web Push 권한 요청, 기기 등록, 발송·실패·결과 불명 상태를 만든다.
10. 날짜·기간·이용 종료·갱신 상태 변경 시 미래 회차와 미발송 알림만 갱신한다.
11. 계정 탈퇴와 항목 삭제 시 관련 미래 작업을 중단한다.

### 선행 결정·검증

- Web Push 결과 불명과 외부 실패의 재시도 횟수·간격
- 브라우저·운영체제·PWA 설치 조건과 실제 전달 동작

### 검증 항목

- 작업을 반복 실행해도 같은 회차와 발송 요청이 중복되지 않는다.
- Push가 불가능해도 앱 안 알림은 유지된다.
- 조용한 시간과 사용자 시간대가 적용된다.
- 날짜 없는 항목은 임의 날짜로 알림을 만들지 않는다.

### 완료 기준

홈·상세·캘린더·알림의 날짜와 상태가 일치하고 외부 전달 실패가 내부 일정에 영향을 주지 않는다.

### 구현 상태 (2026-11-03)

- 월간·주간·목록 캘린더, 결제·갱신·해지 마감·검토·만료·보장 종료 필터와 상세 이동을 구현했다. 현재 등록 필드에 없는 해지 마감 날짜는 임의로 생성하지 않는다.
- 확인된 일자만 `calendar_events`에 만들고, 관리 항목·시간대·채널 변경 시 미래 일정과 미발송 작업을 재생성한다. 서버 작업은 줄어든 12개월 범위를 보충한다.
- 앱 안 알림 기록·읽음 처리와 Web Push 권한·기기 등록/해제를 구현했다. 조용한 시간은 22시~08시이며 의미가 없어진 외부 알림은 건너뛴다.
- 발송 작업은 고유 키와 조건부 선점으로 중복 처리를 막고 `발송·실패·결과 불명·재시도·건너뜀`을 구분한다. 최대 3회, 5분·30분 재시도 정책을 적용했다.
- 실제 Web Push 전달은 운영 HTTPS/PWA 조건, VAPID 키와 정기 작업 호출을 설정한 뒤 브라우저·운영체제별로 검증해야 한다.

## Phase 6. 결합 구독·지출 리포트·인터랙티브 시각화

### 목표

사용자가 앞으로의 비용과 구독 규모를 중복 없이 이해할 수 있게 한다.

### 진행 단계

1. 직접 결제, 포함 혜택, 추가 요금과 금액 미확인 결합 관계를 만든다.
2. 상위 구독과 비용 귀속 항목을 연결하고 같은 비용을 한 번만 합산한다.
3. 선택 기간 시작·종료일을 사용자 시간대로 적용한다.
4. `선택 기간 전체 예정 청구액`과 `선택 기간 중 남은 예정 청구액`을 구분한다.
5. 과거 예정액이 포함되면 실제 결제 여부를 확인하지 않았음을 표시한다.
6. 월 환산액과 근거가 있는 추정 누적액을 별도 계산한다.
7. 취소·건너뜀·금액 미확인 항목의 제외 이유와 개수를 표시한다.
8. 0원과 금액 미확인을 구분하고, 모두 미확인이면 `계산할 정보 없음`을 표시한다.
9. KRW·USD처럼 통화별로 합산하고 자동 환율 변환을 하지 않는다.
10. 지정 기간의 월별 라인 차트와 지난 예정액·미래 예정액을 구분한 막대·표를 만든다.
11. 전체 구독 기간은 버블 차트·그래프·표와 선택 상세를 같은 계산 결과로 제공한다.
12. 모바일, 키보드 조작, 동작 줄이기와 금액 미확인 대체 표시를 확인한다.

### 선행 결정

- 오늘 예정 회차는 사용자 시간대 기준 `남은 예정 청구액`에 포함한다.
- 결합 관계가 있는 상위·하위 항목은 관계를 먼저 해제하기 전까지 삭제하지 않는다.

### 검증 항목

- 결합 구독 비용이 중복되지 않는다.
- 서로 다른 통화가 한 합계나 비용 크기 비교에 섞이지 않는다.
- 기간 라인·막대·표와 전체 기간 버블·그래프·표의 숫자가 각각 일치한다.
- 현재 가격을 과거 실제 지출처럼 표시하지 않는다.

### 완료 기준

사용자가 모든 금액의 의미·근거·제외 항목을 확인할 수 있고 세 시각화 방식의 결과가 일치한다.

### 구현 상태 (2026-11-03)

- `/reports`에 선택 기간 전체·남은 예정 청구액, 금액 미확인·취소/건너뜀·결합 중복 제외 건수와 과거 일정 주의 문구를 구현했다. 오늘 일정은 남은 예정액에 포함한다.
- 결합 관계는 포함 혜택·추가 요금·금액 미확인 연결을 저장하며 비용 귀속 항목만 합산한다. 다른 사용자 항목, 자기 연결, 순환 연결을 차단하고 관계가 남은 항목 삭제를 제한한다.
- 월 환산액은 현재 반복 요금의 비교값으로 계산한다. 추정 누적액은 Phase 6 도입 이후 기록된 가격 구간만 사용하며 현재 가격을 과거 전체에 소급하지 않는다.
- 지정 기간의 월별 증감 라인, 지난 예정액·미래 결제 예정액을 구분한 전체/남은 막대와 표를 구현했다. 전체 구독 기간은 이번 달 결제 금액·구독 개월 수·누적 금액을 버블 차트·그래프·표 순으로 제공하며 그래프와 표를 값 내림차순으로 정렬한다.
- 사용자별 RLS, 가격 구간 트리거, 관계 제약과 DB 테스트를 추가했다. 실제 결제·환불 대사와 Phase 6 이전 가격 이력은 제공하지 않는다.
- 사용자는 선택 기간의 예정 회차를 `예정·취소·건너뜀`으로 관리할 수 있고, 취소·건너뜀은 합계에서 제외된다. 상태 변경 이력은 Phase 6 도입 시점부터 기록하며 이전 가입·종료 이력을 추측하지 않는다.

## Phase 7. Google Calendar 단방향 연동 (제거됨)

2026-11-10 제거 결정으로 구현과 검증 대상에서 제외한다. 기존 단계 내용은 과거 진행 기록이다.

### 목표

내부 일정을 선택적으로 Google Calendar로 보내되 내부 데이터를 항상 원본으로 유지한다.

### 진행 단계

1. 테스트 계정으로 최소 OAuth 권한과 공개 전 검증 필요 여부를 확인한다.
2. 서비스 로그인과 분리된 Google 연결·해제 흐름을 만든다.
3. 동의한 사용자에게 `subscribe-manager` 전용 보조 캘린더를 만든다.
4. 재연결 시 기존 전용 캘린더를 찾아 중복 생성을 막는다.
5. 사용자가 선택한 일정 종류만 내보낸다.
6. 내부 일정과 Google 일정의 연결을 저장해 수정·삭제 대상을 정확히 찾는다.
7. 일반 토큰 만료는 가능한 경우 갱신하고, 권한 철회·갱신 실패 시 재연결을 요청한다.
8. 연결 해제 시 Google 일정을 삭제하거나 유지하는 사용자 선택을 적용한다.
9. 항목 삭제에서 내부 삭제와 Google 일정 삭제 결과를 별도로 표시한다.

### 검증 항목

- 최초 연결·재연결로 캘린더와 일정이 중복되지 않는다.
- 내부 수정·삭제가 연결된 Google 일정에만 반영된다.
- Google에서 직접 수정한 값이 내부로 들어오지 않는다.
- 인증·동기화 실패 중에도 내부 캘린더와 알림이 유지된다.

### 완료 기준

단방향 동기화와 부분 실패 처리가 검증되고, 필요한 외부 심사 상태가 문서에 정확히 표시된다.

### 구현 상태 (2026-11-03)

- `calendar.app.created` 최소 권한의 서버 측 OAuth 연결, 일회성 state 검증, 암호화 토큰 저장과 refresh token 갱신을 구현했다.
- 사용자별 `subscribe-manager` 보조 캘린더 ID를 보존해 재연결 시 재사용하고 내부 source key와 Google event ID 매핑으로 생성·수정·삭제를 멱등 처리한다.
- 설정에서 일정 종류, 즉시 동기화, 일정 삭제/유지 연결 해제를 관리하고 캘린더 화면에 연결 상태를 표시한다. 항목 삭제는 Google 정리 결과를 내부 삭제와 분리해 기록한다.
- 실제 Google Cloud 테스트 프로젝트의 OAuth 동의 화면·테스트 사용자·redirect URI 설정, 외부 공개 전 검증 필요 여부와 운영 스케줄러 호출은 외부 설정 및 실계정 검증이 남아 있다.

## Phase 8. 공식 해지 안내·최신 소식·운영 검수

### 목표

공식 근거가 있는 해지 안내와 구독별 소식을 공통 수집하고 운영자가 검수·공개할 수 있게 한다.

### 진행 단계

1. 제한된 운영 도구와 별도 관리자 화면 중 운영 방식을 확정한다.
2. 초기 운영자와 추가 운영자 권한 범위를 확정한다.
3. 해지 안내의 초안·검수 대기·공개·재확인 필요·비공개 상태를 만든다.
4. 공식 원문 링크, 서비스·국가·요금제·결제 경로, 확인일과 검토자를 기록한다.
5. Apple·Google·통신사 등 실제 결제 경로의 공식 안내를 구분한다.
6. 중요 변경 시 기존 안내를 유지할지 비공개할지 확정해 적용한다.
7. 일반 소식은 정규화된 서비스별 기본 72시간 간격으로 확인하고, 하루 최대 5개 서비스 작업과 비용 한도를 함께 적용한다.
8. 종료일·적용일이 정해진 `임박` 기간에 들어오면 하루 1회로 전환한다.
9. 서비스별 공통 결과를 재사용하고 사용자 새로고침으로 검색을 반복하지 않는다.
10. 소식의 출처·발표일·적용일·국가·요금제·가입 조건·확인일을 저장한다.
11. 공식 출처와 필수 정보가 확인된 소식만 자동 공개하고 불명확한 적용 조건은 `확인 필요`로 표시한다.
12. 검색 실패·새 소식 없음·적용 조건 미확인·원문 실패·예산 제한을 구분한다.
13. 운영자 수정·비공개, 검토자·검토 시각·변경 전후·이유 기록을 만든다.
14. 초기 후보별 소식 지원과 해지 안내 지원을 별도로 검증한다.
15. 후보 밖 서비스는 직접 관리가 가능하되 정보 지원 상태를 정확히 보여준다.

### AI 비용 제한 적용

- 이미지 분석은 사용자당 하루 10회와 예상 US$0.20 중 먼저 도달한 제한을 적용한다.
- 검색·모델 호출은 서비스 전체 하루 US$0.50 제한을 적용한다.
- 개발·시험 누적 US$10 제한을 적용한다.
- 제한에 도달해도 직접 등록과 기존 데이터 조회는 유지한다.
- 호출 전 예상 비용과 진행 중 작업을 고려하고, 예상 비용과 실제 청구가 다를 수 있음을 기록한다.

### 선행 결정·검증

- 운영 도구 형태와 운영자 권한
- 중요 변경된 해지 안내의 공개 방식
- `임박` 기간
- 초기 후보별 공식 자료 접근 가능 여부
- OpenAI 검색·구조화 결과·비용과 프로젝트 접근 권한

### 검증 항목

- 일반 사용자는 운영 작업을 할 수 없다.
- 해지 단계와 URL에는 공식 출처와 확인일이 있다.
- 결제 경로가 다른 안내를 섞지 않는다.
- 일부 OTT 검색 결과를 전체 편성으로 표현하지 않는다.
- 검색 실패와 새 소식 없음이 다르게 보인다.
- 모델·검색 제한 중에도 핵심 관리 기능이 동작한다.

### 완료 기준

지원이 검증된 서비스만 정확한 상태로 공개되고, 출처 없는 절차·URL·적용 조건이 생성되지 않는다.

### 구현 상태 (2026-11-03)

- 운영 방식은 MVP 권장안인 환경변수 allowlist 기반 제한 검수 도구로 구현했다. 일반 사용자에게 운영 API·화면을 노출하지 않고 서버에서 UUID 권한을 다시 검사한다.
- 공통 지원 카탈로그, 결제 경로별 해지 안내, 공통 최신 소식, 수집 결과 상태와 변경 전후 감사 이력을 저장하는 RLS 차단 테이블을 추가했다.
- HTTPS 공식 출처 도메인·확인일·필수 날짜·해지 단계가 없는 자료는 공개할 수 없고, 공개 자료만 사용자 홈·소식 화면·항목 상세에 연결한다. 해지 안내의 `재확인 필요` 상태에서는 확인되지 않은 단계를 숨긴다.
- 중요 변경은 즉시 `재확인 필요`로 전환해 경고와 마지막 확인일만 유지하는 보수적 정책을 적용했다.
- 활성 반복 결제 구독의 별칭을 정규화한 공통 서비스를 수집 대상으로 만들고 OpenAI Responses API 웹 검색을 기본 72시간 간격으로 실행한다. 공식 피드가 설정된 서비스는 조건부 HTTP와 항목 해시로 변경을 먼저 확인한다. 검색에 인용된 HTTPS 공식 원문만 구조화해 저장하며 등록·페이지 조회·더 보기·스크랩은 검색을 실행하지 않는다.
- 자동 소식 수집에는 하루 최대 5개 서비스 작업, 하루 US$0.50·개발 누적 US$10 제한을 적용한다. 호출 전에 토큰·도구 상한 비용을 DB에서 원자 예약하고 응답의 토큰·청구 검색 수로 정산한다. 실제 비용을 확인하지 못하면 예약액을 유지하며 `새 소식 없음`, 사전 확인 실패, 검색·원문 실패, 변경 없음과 예산 제한을 별도 기록한다.
- 운영자가 작성·공개·비공개할 수 있는 전체 사용자 공지사항을 운영자 도구와 홈에 추가했다.
- 전체 소식은 발표별 행을 유지하면서 서비스별 카드로 묶고 기본 2건과 저장 데이터 더 보기를 제공한다. 제목·요약·영향은 한국어 200자 이하로 제한한다. 발표일·적용일·수집일·마지막 확인일을 분리하고, 사용자 국가·시간대 자료를 우선 검색하며 원문 국가/글로벌 범위와 원문 언어를 표시한다. OTT 공식 공개 예정작·신규/종료 편성은 공식 발표 단위로 묶는다.
- 공통 소식과 사용자 관계만 저장하는 개인 스크랩, 서비스·종류 필터, 최신 스크랩순 목록과 내비게이션 진입점을 추가했다. 구독 종료 후에도 유지하고 계정 탈퇴 시 삭제하며, 비공개 소식은 본문 대신 제공 중단 안내를 표시한다.
- 내비게이션 진입점을 `소식`으로 바꾸고 최신 소식 안의 `스크랩` 버튼으로 보관함에 이동하도록 정리했다. 모바일 하단 내비게이션은 데스크톱 메뉴가 숨는 860px 이하에서 항상 표시하고 safe-area와 본문 하단 여백을 적용한다.
- 구독 여부와 관계없는 9개 OTT 공식 공개 예정작 공통 피드를 최신 소식 상단에 추가했다. 기존 72시간·하루 5개·비용 제한을 공유하며 국내 공식 발표와 서비스별 대표 소식만 노출한다.
- 일반 소식 12개월·OTT 편성 90일 보관 전환과 미스크랩 보관 소식 24개월 삭제 작업을 수집 스케줄에 연결했다. 스크랩된 보관 소식은 삭제하지 않는다.

## Phase 9. 통합 검증과 MVP 출시 준비

### 목표

기능별로는 성공하지만 함께 사용할 때 깨지는 상태를 찾아 수정하고, 외부 조건과 운영 준비를 최종 확인한다.

### 통합 검증 순서

1. 새 사용자가 가입·이메일 확인·로그인을 완료한다.
2. 날짜·금액이 없는 구독과 모든 생활 기한 유형을 직접 등록한다.
3. 이미지를 분석하고 사용자가 초안을 수정해 저장한다.
4. 목록·홈·상세·캘린더의 날짜와 상태가 일치하는지 확인한다.
5. 12개월 예상 일정과 앱 알림·Web Push를 확인한다.
6. 결합 구독, 통화별 리포트와 기간 차트·버블·그래프·표를 비교한다.
8. 공식 해지 안내와 최신 소식의 출처·상태·사용자 관련성을 확인한다.
9. 사용 완료·휴지통·복원·30일 삭제 대상과 파일 실패 처리를 확인한다.
10. 항목 삭제에서 내부 성공, 이미지 실패와 Google 실패의 부분 결과를 확인한다.
11. 계정 탈퇴 즉시 접근 중단과 24시간 내 개인 자료 삭제 목표를 확인한다.

### 비기능 검증

- 모바일 주요 화면과 다양한 화면 크기
- 키보드 조작, 상태 텍스트, 동작 줄이기와 표 대체 보기
- 사용자 간 접근 차단과 비공개 이미지 접근
- 월말·윤년·시간대 경계
- 반복 작업의 중복 방지와 실패 재시도
- 외부 API 장애와 비용 한도 도달 시 핵심 기능 유지
- 지원 서비스·권한·요금·외부 심사 상태의 최종 문서 반영

### 출시 전 문서 확인

1. 확정된 정책을 PRD와 spec에 반영한다.
2. 외부 검증 결과와 검증 날짜를 기록한다.
3. 지원 완료·검증 중·지원하지 않음 상태를 초기 카탈로그에 표시한다.
4. 사용자에게 이미지 외부 전송, 원본 보관, 알림 권한과 계정 탈퇴 삭제 범위를 안내한다.
5. 후속 기능이 MVP 화면에서 실제 기능처럼 보이지 않게 한다.

### MVP 최종 완료 기준

- Phase 1~8의 완료 기준을 모두 통과한다.
- `spec.md`의 사용자 행동·정상 결과·실패 처리·권한·확인 기준을 통합 시나리오에서 확인한다.
- 미정 정책이 임의 기본값으로 구현되어 있지 않다.
- 외부 검증이 끝나지 않은 기능을 지원 완료로 표시하지 않는다.
- 실제 결제·환불·해지 실행과 OTT 추천이 MVP에 포함되지 않는다.

## 4. MVP 이후로 유지할 기능

다음 기능은 이 개발 계획에 포함하지 않는다.

- OTT 취향 설문, `보고 싶어요`, 추천 점수와 OTT 조합 추천
- 관심 작품 커버리지와 절약액 시뮬레이션
- 실제 결제 거래와 영수증 대사
- 부분·분할 결제와 환불 거래 처리
- 환율 API 자동 원화 환산
- 할인·결제 경로 비교, 게이미피케이션과 위젯
- 은행·카드·앱스토어 자동 연동
- 이메일·메신저 알림
- Google Calendar 연동

MVP의 OTT 최신 소식, 입력 폼·이미지 등록, 예상 지출, Web Push, 해지 안내와 인터랙티브 시각화는 계획에서 제외하지 않는다.
