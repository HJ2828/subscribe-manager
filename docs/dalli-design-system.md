# 달리 디자인 리뉴얼 — Codex 작업 요청

당신은 UI/UX 디자이너이자 React 프론트엔드 엔지니어입니다. 진행 중인 구독·생활 기한 관리 서비스의 디자인을 아래 기준으로 개선하고 실제 코드에 적용해 주세요. 아이디어 제안에 그치지 말고, 현재 저장소 구조와 구현 상태를 확인한 뒤 작업을 완료해 주세요.

## 1. 작업 목적과 자료 우선순위

- 서비스 이름: **달리**
- 이름의 의미: 달마다 돌아오는 구독·결제·기프티콘 기한 관리. ‘다달이 → 다다리 → 달리’에서 출발한 이름입니다.
- 브랜드 콘셉트: **흩어진 구독과 기한을 나만의 작은 우주에.**
- 목표: 밝고 정돈된 화면, 읽기 쉬운 날짜·금액, 일관된 컴포넌트, 절제된 우주 디테일을 갖춘 서비스로 개선합니다.
- 이번 작업은 **디자인 리뉴얼**입니다. 신규 서비스나 별도 데모 앱을 만들지 마세요.

함께 첨부하는 자료:

1. `PRD.md`, `spec.md`, `plan.md`: 기능·정책·개발 진행 참고
2. `DESIGN-mintlify.md`: 레이아웃·여백·타이포 위계·컴포넌트 디자인 참고
3. `color-palette.jpeg`: 달리 브랜드 팔레트
4. `moon.png`, `ailen.png`, `moon_remove_bg.png`, `ailen_remove_bg.png`: 보조 캐릭터 참고

파일명이 다르면 내용으로 대응 자료를 찾으세요. 저장소의 AGENTS.md와 현재 문서·컴포넌트·라우트·스타일을 먼저 확인하세요. 첨부 문서의 완료 기록은 현재 코드와 대조하고, 기록만으로 구현 또는 외부 연동 검증 완료를 가정하지 마세요.

우선순위는 이 요청의 명시적 디자인 조건 → 현재 제품 기능·정책 → Mintlify 디자인 참고입니다. Mintlify의 원래 색상·폰트·개발자 문서 레이아웃을 그대로 복제하지 마세요.

## 2. 반드시 지킬 방향

- 이번 작업은 색상 변경이 아니라 전반적인 UI/UX 리디자인입니다.
- 기존 기능·데이터·API·인증·권한·제품 정책은 유지합니다.
- 레이아웃·정보 위계·컴포넌트 배치·크기·padding·margin·문구는 재설계합니다.
- 필요하면 JSX와 프론트엔드 컴포넌트 구조도 변경합니다.
- 기존 코드 재사용은 기존 화면 배치를 유지하라는 뜻이 아닙니다.
- 색상·테두리·모서리만 변경한 결과는 완료로 인정하지 않습니다.
- 사이트 전체는 밝은 배경을 유지합니다. 다크 섹션과 어두운 푸터를 만들지 않습니다.
- 헤더·요약 카드 등에 절제된 글래스모피즘을 적용합니다.
- 제공한 캐릭터 이미지는 반드시 실제 화면에 사용합니다.
  ‘보조용’은 작게 사용하라는 의미이며 생략을 허용하는 뜻이 아닙니다.
- 모든 페이지에 공통 레이아웃·타이포그래피·간격·컴포넌트 규칙을 적용합니다.
- 네온·강한 추가 발광·빽빽한 별 배경·무거운 3D 배경은 사용하지 않습니다.
- 미구현 기능을 동작하는 것처럼 표시하거나 실제 데이터를 예시 데이터로 교체하지 않습니다.

## 3. 디자인 시스템

기존 테마 구조에 맞춰 공통 토큰을 정의하고 재사용하세요. 페이지마다 임의의 색상·그림자·모서리를 추가하지 마세요.

| 역할 | 기준 |
| --- | --- |
| 페이지 바탕 | `#F3F9FF` 또는 흰색 |
| 헤더·요약 카드·부유 패널 | 반투명 흰색, 약한 배경 블러, 은은한 테두리 |
| 일반 목록·표·폼·입력창 | 가독성을 우선한 흰색 또는 거의 불투명한 흰색 |
| 브랜드 주요색 | `#002D80`: 주요 CTA, 선택된 내비게이션, 핵심 제목 |
| 브랜드 보조색 | `#6A3EA3`: 보조 그래픽, 제한적인 선택 강조 |
| 연노랑 | `#FFF1AD`: 달과 브랜드 장식 |
| 연초록 | `#C3F0BD`: 외계인, 완료·확인 상태의 작은 강조 영역 |
| 본문 | 가독성이 높은 짙은 중립색 |
| 경계선 | 밝은 회청색 계열의 얇은 1px 선 |
| 그림자 | 약한 그림자, 랜딩의 제품 미리보기에 한해 조금 더 강조 |

- 브랜드 보조색과 시스템 상태색의 역할을 구분하세요. 오류·위험·삭제에는 필요한 의미 색상을 별도로 사용합니다.
- 연노랑·연초록 위에는 짙은 글자를 사용하세요. 작은 글자에 파스텔색을 사용하지 마세요.
- 카드 반경은 12~16px, 작은 입력 요소는 8~12px 범위로 통일합니다. 주요 CTA는 캡슐형으로 만들되 모든 작은 조작 버튼을 캡슐형으로 강제하지 마세요.
- 간격은 4/8/12/16/24/32/48/64px 체계로 정리합니다.
- 관리 화면에는 랜딩 수준의 거대한 여백을 적용하지 말고, 날짜와 금액을 빠르게 비교할 수 있는 밀도를 유지합니다.

### 공통 레이아웃과 간격

- 공통 AppShell과 PageHeader를 정의하고 모든 내부 페이지에 적용합니다.
- 데스크톱 내비게이션 방식은 현재 메뉴 수와 화면 폭을 검토해 정하되,
  내부 페이지마다 헤더·내비게이션 구성이 달라지지 않게 합니다.
- 데스크톱 콘텐츠는 최대 너비 1200~1280px를 기준으로 정렬합니다.
  캘린더·넓은 표처럼 공간이 필요한 화면은 공통 확장형 레이아웃을 사용합니다.
- 콘텐츠 좌우 여백은 데스크톱 32~48px, 모바일 16~20px를 기준으로 합니다.
- 페이지 상단은 제목·설명을 왼쪽, 주요 행동 버튼을 오른쪽에 배치합니다.
- 모바일에서는 제목·설명 다음 줄에 주요 행동 버튼을 배치합니다.
- 검색·필터·정렬은 페이지 제목 아래의 공통 도구 영역으로 묶습니다.
- 카드 내부 여백은 데스크톱 24px, 모바일 16~20px를 기준으로 합니다.
- 카드 간격은 16~24px, 큰 섹션 간격은 32~48px를 기준으로 합니다.
- 폼은 최대 너비 720~800px를 기준으로 하고 관련 입력끼리 묶습니다.
- 동일한 용도의 버튼·입력창·배지·모달·빈 화면은 공통 컴포넌트를 사용합니다.
- 랜딩과 내부 관리 화면은 정보 밀도를 구분하되 같은 디자인 토큰을 사용합니다.

### 밝은 글래스모피즘

- 헤더·홈 요약 카드·일부 부유 패널에 실제 반투명 효과를 적용합니다.
- 기준값은 흰색 불투명도 72~88%, backdrop-filter blur 12~16px,
  은은한 테두리와 약한 그림자입니다.
- 뒤쪽에 매우 옅은 하늘색·보라색 그라데이션을 제한적으로 배치해
  반투명 효과가 드러나게 합니다.
- 긴 목록·표·등록 폼 전체에 블러를 반복 적용하지 않습니다.
- 입력창은 거의 불투명하게 유지하고 입력값·레이블의 대비를 확보합니다.
- 블러를 지원하지 않는 환경에는 충분히 불투명한 배경을 제공합니다.
- 글래스 효과 때문에 텍스트나 상태 배지의 가독성이 떨어지지 않게 합니다.

### 문구

- 페이지 제목·설명·버튼·입력 안내·빈 화면 문구도 수정 대상입니다.
- 제목은 화면의 목적을, 설명은 사용자가 할 수 있는 일을 짧게 전달합니다.
- 버튼에는 ‘확인’ 같은 모호한 표현보다 ‘구독 등록’, ‘변경 사항 저장’처럼
  실제 행동을 표시합니다.
- 같은 행동과 상태에는 페이지가 달라도 같은 용어를 사용합니다.
- 중복 설명과 불필요한 개발 용어를 줄입니다.
- 예상 금액·금액 미확인·부분 실패 등 제품 정책상 필요한 의미는 보존합니다.

### D-day 강조색과 오류·상태색

브랜드 팔레트와 별도로 아래 의미 색상을 공통 토큰으로 정의하세요. 홈·목록·상세·캘린더에서 같은 상태에 같은 색을 적용합니다.

| 용도 | 글자·아이콘 | 연한 배경 | 표시 예시 |
| --- | --- | --- | --- |
| 일반 일정: 8일 이상 남음 | `#002D80` 네이비 | `#EAF1FF` | `D-30`, `D-8` |
| 일주일 이내: 4~7일 남음 | `#92400E` 앰버 | `#FEF3C7` | `D-7`, `D-4` |
| 임박: 0~3일 남음 | `#C2410C` 오렌지 | `#FFF0E5` | `D-3`, `D-1`, `D-day` |
| 오류·실패 | `#B42318` 레드 | `#FEF3F2` | 저장 실패, 입력 오류 |
| 만료·종료 | `#667085` 회색 | `#F2F4F7` | 기한 만료, 이용 종료 |

- D-day 배지는 연한 배경과 진한 글자, 굵기 600~700을 사용합니다. 숫자를 강조하되 카드 전체를 강조색으로 채우지 마세요.
- **기한 임박은 오렌지, 오류는 레드**로 구분합니다. 예정 결제일이 가깝다는 이유만으로 오류·실패처럼 표시하지 마세요.
- 브랜드 연노랑 `#FFF1AD`는 달과 장식에 사용하고, 기한 배지는 위의 앰버·오렌지 계열로 통일합니다.
- 입력 오류는 빨간 테두리·오류 아이콘·구체적인 안내 문구를 함께 사용합니다. 상태를 색상만으로 전달하지 마세요.
- 만료·종료는 회색으로 표현하고, 필요한 행동이 있으면 별도 버튼을 제공합니다. 경과한 반복 결제 예정일을 임의로 이용 종료나 기한 만료로 바꾸지 마세요.
- D-day와 상태 판단은 기존 제품의 사용자 시간대·날짜 정밀도·상태 정책을 그대로 사용합니다. 날짜 미확인 항목에 임의 D-day를 만들지 마세요.
- 확인 필요·부분 성공은 오류와 구분해 앰버 계열과 상태 문구로 안내합니다. 실제 실패한 작업은 해당 부분에만 오류색을 적용합니다.
- 삭제 같은 파괴적 행동에는 레드 계열을 사용할 수 있지만 일반 취소·뒤로 가기 버튼에는 적용하지 마세요.
- 텍스트 대비와 포커스 표시를 확인하고, 빨간 오류 테두리만으로 안내를 대신하지 마세요.

### 폰트

**Pretendard Variable**을 전체 UI의 기본 폰트로 사용합니다.

사용자가 제공한 CDN:

`https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/dist/web/static/pretendard.min.css`

이 주소는 static 경로이므로, 실제 Variable 사용 여부를 확인하세요. 기존 프로젝트의 Variable 에셋이 있으면 재사용하고, 없으면 동일 배포 버전의 올바른 Variable 리소스를 확인해 적용하세요. 제공 주소를 사용하면서 Variable을 적용했다고 잘못 보고하지 마세요. 외부 리소스를 확인할 수 없다면 가능한 폴백을 적용하고 제한을 보고하세요.

- 랜딩 제목: 데스크톱 56~64px / 모바일 36~40px, 600~700, 행간 약 1.2
- 내부 화면 제목: 28~32px, 600~700
- 본문·입력값: 16px, 행간 1.5~1.6
- 보조 정보: 13~14px, 충분한 명도 대비
- 버튼: 15~16px, 500~600
- 금액·날짜 정렬에는 필요 시 tabular-nums를 적용합니다.

## 4. 화면별 적용

### 랜딩 / 비로그인 진입 화면

기존 공개 진입 화면이 있으면 해당 화면을 개선하세요. 로그인 후 홈과 랜딩은 구분합니다. 공개 랜딩이 없다면 이번 작업을 위해 새 라우트를 임의로 추가하지 말고 내부 서비스 리뉴얼을 우선하세요.

- 밝은 헤더: 달리 로고, 필요한 최소 메뉴, 로그인·시작 버튼
- 중앙 정렬의 짧은 제목 → 설명 → CTA → 넓은 실제 제품 미리보기
- 제목 제안: **흩어진 구독과 기한을, / 나만의 작은 우주에.**
- 설명 제안: **구독 결제부터 기프티콘 만료일까지, 다가오는 일정과 예상 비용을 한곳에서 확인하세요.**
- 주요 CTA: `달리 시작하기`. 기존 가입 또는 시작 경로에 연결합니다.
- 보조 CTA: `미리 둘러보기`. 실제 미리보기 섹션이 있을 때만 제공합니다.
- 제품 미리보기는 예정 결제 금액·다가오는 일정·미니 캘린더를 중심으로 구성합니다. 예시 데이터에는 예시임을 표시합니다.
- 하단은 통합 관리 → 등록 방식 → 예상 지출 → 시작 안내 순서로 간결하게 구성합니다.
- 지원하지 않는 자동 금융 연결·결제·해지 실행을 암시하지 마세요. 가짜 후기·이용자 수·절약 수치를 넣지 마세요.

### 로그인 후 홈

- 상단에 페이지 제목·짧은 설명·등록 버튼을 배치합니다.
- 제목 옆에 작은 달 캐릭터를 배치합니다.
- 다음 30일 예정 결제 금액·결제 건수·만료 예정 혜택을 요약 카드로 구성합니다.
- 데스크톱에서는 다가오는 일정과 미니 캘린더를 2열로 배치하고,
  일정 영역에 더 넓은 공간을 제공합니다.
- 모바일에서는 요약 → 다가오는 일정 → 캘린더 순서로 쌓습니다.
- 확인 필요 항목은 별도 영역으로 묶고 필요한 수정 행동으로 연결합니다.
- 관련 소식과 공지는 핵심 일정 아래에 배치합니다.
- 큰 환영 카드가 금액과 일정을 아래로 밀지 않게 합니다.

### 관리 목록

- 제목과 등록 버튼 → 검색·필터·정렬 → 결과 건수와 목록 순서로 배치합니다.
- 서비스명·유형·금액·다음 일정·D-day·상태의 위치를 일관되게 정렬합니다.
- 이름이 길거나 금액이 없는 항목도 정렬이 무너지지 않게 합니다.
- 모바일에서는 이름·다음 일정·D-day를 우선 노출하고 나머지 정보를 아래에 배치합니다.
- 기존 카드·목록 전환 기능이 있으면 유지합니다.

### 상세

- 상단에 항목 이름·유형·핵심 상태와 수정 버튼을 배치합니다.
- 날짜·금액·결제 주기를 먼저 보여주고 부가 정보는 아래에 묶습니다.
- 이용 상태·자동 갱신·사용자 계획은 각각 구분합니다.
- 이미지·이력·결합 관계·해지 안내 등 기존 정보는 관련 섹션으로 정리합니다.
- 삭제는 일반 수정 행동과 분리하고 영향 안내를 유지합니다.

### 등록·수정

- 기본 정보 → 금액·주기 → 날짜·알림 → 부가 정보 순서로 입력을 묶습니다.
- 관리 유형별로 필요한 입력을 보여주는 기존 동작을 유지합니다.
- 데스크톱에서는 관련된 짧은 입력만 2열로 배치하고 모바일에서는 1열로 구성합니다.
- 레이블·도움말·오류 문구의 위치와 간격을 통일합니다.
- 이미지 등록은 데스크톱에서 이미지와 추출 초안을 나란히,
  모바일에서는 이미지 다음에 초안을 배치합니다.
- 저장 버튼은 입력 흐름 마지막에 명확하게 배치합니다.
- AI 초안을 사용자 확인 없이 확정 정보로 표시하지 않습니다.

### 캘린더

- 제목 → 월 이동·오늘·보기 방식 → 일정 유형 필터 → 캘린더 순서로 구성합니다.
- 선택 날짜와 오늘 날짜를 서로 다른 표현으로 구분합니다.
- 일정 유형은 색과 텍스트를 함께 사용합니다.
- 모바일에서는 날짜 셀 안에 긴 문구를 넣지 않고 선택 날짜의 목록에서 상세를 제공합니다.
- 기존 월간·주간·목록 보기와 상세 이동을 유지합니다.

### 리포트

- 제목 → 기한·통화 선택 → 핵심 지표 → 차트 → 상세 내역·계산 근거 순서로 구성합니다.
- 각 지표의 이름·금액·설명 위치를 통일합니다.
- 버블 차트에는 절제된 행성 표현을 적용하고 선택 상세를 가까운 위치에 표시합니다.
- 그래프·표 대체 보기와 키보드 조작을 유지합니다.
- 장식 때문에 데이터 크기나 금액의 의미를 왜곡하지 않습니다.

### 소식·스크랩·해지 안내

- 페이지 제목 아래에 서비스·종류 필터를 공통 형태로 배치합니다.
- 소식은 서비스별 묶음을 유지하고 카드 내부 구조를 통일합니다.
- 서비스명 → 제목 → 요약·영향 → 날짜·출처 순서로 정보 위계를 정리합니다.
- 스크랩 버튼은 같은 위치에 배치하고 저장 여부를 명확히 표시합니다.
- 해지 안내는 결제 경로·확인일·공식 출처·재확인 상태를 읽기 쉽게 묶습니다.
- 조회·더 보기·필터·스크랩은 기존 저장 데이터를 사용하며 새 AI 검색을 유발하지 않습니다.

### 계정·설정·공통 상태

- 회원 관련 화면에도 공통 버튼·입력창·레이블·오류 스타일을 적용합니다.
- 설정은 계정·지역과 통화·알림·연동·파일 관리 등 관련 항목끼리 묶습니다.
- 로딩·빈 데이터·오류·완료·확인 필요·부분 성공의 디자인을 통일합니다.
- 빈 화면과 등록 완료에는 5절에 지정한 캐릭터를 반드시 적용합니다.

## 5. 캐릭터와 인터랙션

### 제공 에셋

- `moon.png`, `ailen.png`: 어두운 배경이 포함된 원본 참고 이미지
- `moon_remove_bg.png`, `ailen_remove_bg.png`: 실제 UI에 사용할 투명 배경 이미지

투명 배경 파일을 우선 사용합니다.
실제 파일명이 다르면 제공된 파일을 확인해 대응 에셋을 사용합니다.
원본의 어두운 배경에 맞추기 위해 사이트를 어둡게 만들지 않습니다.

### 필수 배치

캐릭터 사용은 필수입니다.
보조용은 크기와 비중을 제한한다는 뜻이며 생략을 허용하지 않습니다.

| 위치 | 캐릭터 | 기준 크기 |
| --- | --- | --- |
| 로그인 후 홈 제목·요약 영역 | 달 | 데스크톱 64~88px, 모바일 40~56px |
| 관리 목록·소식·스크랩의 빈 화면 | 외계인 | 80~112px |
| 기존 등록 완료 안내 | 달 또는 외계인 | 32~48px |

- 홈의 달은 데이터 유무와 관계없이 보이게 합니다.
- 핵심 금액·일정·버튼을 가리거나 아래로 밀지 않게 합니다.
- 빈 화면에는 안내 문구와 필요한 행동 버튼을 함께 배치합니다.
- 등록 완료 캐릭터를 위해 별도 모달이나 대기 시간을 추가하지 않습니다.
- 제공 이미지를 일반 아이콘·CSS 도형으로 대체하지 않습니다.
- 파일을 복사하는 것에 그치지 말고 실제 컴포넌트에 연결합니다.

### 이미지 표현

- 기존 캐릭터 형태·색감·비율을 유지합니다.
- 투명 배경과 에셋에 포함된 Glow를 보존합니다.
- 강한 추가 발광이나 어두운 사각 배경을 넣지 않습니다.
- 투명 여백 때문에 캐릭터가 지나치게 작게 보이지 않도록 조정합니다.
- 캐릭터와 Glow가 컨테이너 경계에서 잘리지 않게 합니다.
- 장식용 이미지는 빈 alt를 사용하고 필요한 안내는 텍스트로 제공합니다.
- 파일이 없으면 누락 파일을 보고하고 해당 적용을 미완료로 기록합니다.

### 인터랙션

- 버튼·탭 전환은 약 150~200ms로 절제합니다.
- 행성 시각화는 포인터·탭·키보드로 선택할 수 있게 합니다.
- 자동 회전·커서 추적·강한 패럴랙스는 추가하지 않습니다.
- prefers-reduced-motion을 반영합니다.

## 7. 진행 방식과 검증

1. 현재 저장소와 작업 트리, 적용 범위를 확인합니다. 기존 사용자 변경을 덮어쓰지 마세요.
2. 현재 홈과 관리 목록을 확인하고, 레이아웃·정보 위계·간격·배치·문구를 어떻게 바꿀지 짧게 설명한 뒤 구현합니다. 두 화면에서 공통 디자인을 확립하고 나머지 페이지까지 적용합니다. 두 화면만 수정하거나 계획만 제시하고 종료하지 않습니다. 통상적인 디자인 선택마다 승인을 요청하지 않습니다.
3. 공통 토큰·폰트·컴포넌트 → 홈 → 목록·상세·폼 → 캘린더·리포트 → 소식·스크랩 → 계정·기타 화면 순으로 적용합니다. 공개 랜딩이 있으면 같은 스타일로 개선합니다.
4. 기존 라우팅·상태 관리·API 연결과 현재 기술 스택을 재사용합니다. 대규모 라이브러리나 구조 재편은 피합니다.
5. 1440px 데스크톱과 390px 모바일을 기준으로 주요 화면을 시각적으로 확인합니다. 좁은 화면의 가로 넘침·날짜 잘림·버튼 겹침도 확인합니다.
6. 터치 영역은 주요 조작 기준 최소 44px를 확보하고, 포커스·키보드 조작·텍스트 대비·오류 안내를 확인합니다.
7. 프로젝트에서 사용하는 타입 검사·린트·빌드를 실행합니다. 스타일만 검증하는 불필요한 테스트를 늘리지 말고, 변경된 상호작용에는 필요한 기존 검증을 수행합니다.
8. 로그인·외부 연동 등 실제 확인이 불가능한 부분은 검증 완료로 보고하지 마세요.
