# subscribe-manager 기능 동작 설명서

작성일: 2026-11-02

기준 문서: `docs/PRD.md`

이 문서는 PRD의 MVP 기능이 사용자에게 어떻게 동작해야 하는지 설명한다. 구현 기술보다 사용자의 행동과 결과를 중심으로 작성한다.

## 공통 원칙

- 등록 방법은 입력 폼과 이미지 업로드 두 가지다. 문장·대화형 등록은 제공하지 않는다.
- 사용자는 자신의 구독, 생활 기한, 이미지와 관심 정보만 볼 수 있다.
- 확인할 수 없는 날짜·금액·통화는 추측하지 않고 `확인 필요`로 표시한다.
- 실제 결제, 환불과 구독 해지는 사용자가 외부 서비스에서 직접 한다.
- 외부 서비스의 실제 지원 여부를 확인하기 전에는 `지원 완료`로 표시하지 않는다.

## 1. 회원가입과 이메일 확인

### 회원가입 입력 조건

| 입력 항목 | 필수·선택 | 허용 형식과 범위 | 빈 값·확인 필요 | 잘못 입력했을 때 안내 | 값이 없을 때 제한 |
| --- | --- | --- | --- | --- | --- |
| 이메일 | 필수 | 이메일 주소 형식. 최대 길이는 확인 필요 | 빈 값 불가 | `이메일 주소 형식을 확인해 주세요.` 또는 중복 가입 안내 | 가입·로그인·이메일 확인 불가 |
| 비밀번호 | 필수 | Supabase Auth에 설정할 최소 길이·문자 조합은 확인 필요 | 빈 값 불가 | 충족하지 못한 비밀번호 조건을 표시 | 가입·로그인 불가 |
| 이메일 확인 | 필수 | 발송된 확인 링크 사용. 링크 유효시간은 외부 설정 검증 필요 | `확인 필요` 상태 허용 | 만료·오류 시 새 확인 메일 요청 안내 | 보호된 화면 이용 불가 |

1. **입력·행동:** 사용자는 이메일과 비밀번호를 입력해 가입하고, 받은 이메일의 확인 링크를 누른다.
2. **정상 결과:** 계정이 만들어지고 이메일 확인 후 로그인할 수 있다. 기본 국가는 대한민국, 통화는 원화, 시간대는 `Asia/Seoul`로 시작한다.
3. **실패 처리:** 이메일 형식, 비밀번호 조건과 중복 이메일 문제를 해당 입력란에 설명한다. 확인 메일 발송 실패 시 다시 요청하게 한다. 이메일 확인 전에는 보호된 화면을 사용할 수 없다.
4. **권한:** 가입한 본인만 자신의 계정을 사용할 수 있다. 비밀번호는 화면에서 조회할 수 없다.
5. **확인 기준:** 가입, 이메일 확인과 첫 로그인이 이어져야 한다. 잘못된 입력과 중복 이메일에서는 새 계정이 생기지 않아야 한다.

## 2. 로그인·로그아웃·비밀번호 재설정

1. **입력·행동:** 이메일·비밀번호로 로그인하고, 필요하면 로그아웃하거나 비밀번호 재설정 이메일을 요청한다.
2. **정상 결과:** 로그인하면 본인의 통합 홈으로 이동한다. 로그아웃하면 본인 데이터가 보이지 않는다. 재설정 후에는 새 비밀번호로 로그인할 수 있다.
3. **실패 처리:** 로그인 정보가 맞지 않으면 다시 입력하게 한다. 재설정 링크가 만료됐으면 새 링크를 요청하게 한다.
4. **권한:** 로그인한 본인만 자신의 데이터에 접근한다. Google Calendar 인증은 서비스 로그인과 별개이며 Google 소셜 로그인은 MVP 필수가 아니다.
5. **확인 기준:** 정상·실패 로그인, 로그아웃과 비밀번호 재설정을 각각 확인한다. 로그아웃 후 이전 사용자 데이터가 보이면 안 된다.

## 3. 설정과 계정 탈퇴

1. **입력·행동:** 사용자는 국가·통화·시간대·알림 기본값을 바꾸고 저장 용량을 확인한다. 탈퇴할 때는 탈퇴 버튼과 최종 확인을 누른다.
2. **정상 결과:** 설정값이 화면과 알림에 반영된다. 탈퇴 확인 즉시 로그아웃되고 접근·알림·사용자별 소식 처리가 중단된다. 개인 이미지, 관리 이력, 추출 초안과 관심 정보는 요청 후 24시간 이내 삭제를 목표로 한다.
3. **실패 처리:** 잘못된 설정값은 저장하지 않는다. 삭제 실패는 기록하고 재시도한다. 외부 제공자의 보관 자료와 백업 삭제 범위는 서비스 데이터 삭제와 다를 수 있음을 알린다.
4. **권한:** 본인만 설정을 변경하고 탈퇴할 수 있다. 공통 소식과 해지 안내는 특정 사용자 소유가 아니므로 유지할 수 있다.
5. **확인 기준:** 설정 변경이 실제 화면에 반영되어야 한다. 탈퇴 즉시 접근할 수 없어야 하며, 24시간 안에 삭제되거나 실패 재시도 상태가 남아야 한다.

## 4. 입력 폼으로 직접 등록

### 모든 등록 폼에 적용하는 조건

- 현재 저장 검증에서 필수인 관리 유형과 식별 이름에는 `*`를 표시한다. 금액 입력으로 통화가 필수가 되는 것처럼 조건부 필수 항목도 조건이 성립하면 `*`를 표시한다.
- 제목·서비스명 같은 식별값의 필수 여부와 글자 수는 `확인 필요`다.
- 금액은 숫자 `0`과 `금액 미확인`을 구분한다. 사용자가 0원임을 확인한 경우만 0으로 저장하고, 모르면 빈 값과 `확인 필요` 상태로 저장한다. 소수점·최대 금액 범위는 `확인 필요`다.
- 직접 등록과 이미지 등록의 결제 통화 선택은 KRW로 시작하며 사용자가 실제 통화로 바꿀 수 있다. 이미지 분석에서 통화가 명확히 확인되면 해당 추출값으로 바꾸고 `이미지에서 입력됨`으로 표시한다. 금액이 있으면 결제 통화를 함께 입력하고, 통화가 없으면 통화별 합계와 비용 기준 시각화에서 제외한다.
- 날짜는 일자, 연·월처럼 확인된 정밀도를 그대로 저장한다. 허용 가능한 과거·미래 범위는 `확인 필요`다.

### 기타 결제 기한

반복 결제 구독과 같은 금액·통화·결제 주기·날짜·상태·결제 경로·알림 입력을 사용한다. 식별 필드의 라벨은 `결제 이름`, 시작 날짜 라벨은 `최초 결제일`이며 요금제 필드는 사용하지 않는다. 유형 선택에서는 `기타 기한` 바로 위에 배치한다. 확인된 결제일과 반복 주기는 홈의 예정 결제, 내부 캘린더와 알림에 결제 일정으로 반영한다.

5. **확인 기준:** 유형마다 입력란이 달라야 한다. 저장값이 목록·상세·홈·캘린더에서 일치하고 미확인 값이 임의 값으로 바뀌지 않아야 한다.

## 5. 이미지로 등록 초안 만들기

업로드 대상은 계정·멤버십, 요금제, 결제·갱신 안내, 영수증·결제 내역, 기프티콘·쿠폰·상품권과 보증 안내 이미지다.

1. **입력·행동:** 직접 등록 폼 우측의 이미지 등록 토글을 켜고 JPEG·PNG·WebP 이미지를 선택한다. 필요하면 자르거나 개인정보를 가리고 외부 AI 전송 범위와 원본 보관 여부를 확인한 뒤 분석한다. 기존 항목 수정에서는 새 원본을 첨부·보관할 수 있지만 자동 분석은 실행하지 않는다.
2. **정상 결과:** 이미지에서 확인되는 서비스명, 요금제, 금액·통화, 날짜, 사용처와 조건이 폼 초안에 들어간다. 이미지와 초안을 나란히 보고 수정·확정해야 관리 항목으로 저장된다.
   분석 후 관리 유형을 바꾸면 이미지 자산의 유형도 함께 바꾸고 새 유형의 공통 폼을 표시한다. 이름·금액·통화·날짜·카테고리·메모처럼 새 유형에도 대응 입력란이 있는 분석값과 사용자 수정값은 유지한다. 새 유형에 존재하지 않는 전용 필드만 제외하며, 원하면 변경한 유형으로 다시 분석할 수 있다.
3. **실패 처리:** 지원하지 않는 형식, 손상 파일과 10MB 초과 파일은 이유를 알리고 분석하지 않는다. 없는 값은 추측하지 않는다. `2025년 1월`은 특정 일자로 바꾸지 않는다. 통화가 불명확하면 확인을 요청한다. 분석 실패·한도 도달 시 직접 입력을 제공한다.
4. **권한:** 올린 본인만 이미지와 초안을 본다. 이메일·전화번호·주소·계정 ID는 추출 필드로 저장하지 않는다. 가리지 않은 개인정보가 이미지와 함께 외부 AI에 전송될 수 있음을 미리 알린다.
5. **확인 기준:** 보이는 값만 초안에 들어가고, 사용자 확정 전에는 실제 항목이 생기지 않아야 한다. 원본과 결과를 비교·수정할 수 있어야 한다.

## 6. 이미지 보관과 저장 한도

1. **입력·행동:** 사용자는 원본 보관 여부를 선택하고 사용 용량을 확인하며 파일을 정리한다.
2. **정상 결과:** 파일당 10MB, 사용자당 총 100MB까지 저장한다. 100MB에는 원본·분석용·임시·휴지통 파일이 모두 포함된다. 구독 화면은 원본 삭제, 기프티콘·상품권·보증은 원본 보관을 기본 제안하되 사용자가 바꿀 수 있다.
3. **실패 처리:** 100MB를 넘으면 기존 파일을 자동 삭제하지 않고 정리를 안내한다. 등록 취소 파일은 즉시 삭제 대상으로, 미저장 이미지와 초안은 마지막 활동 24시간 후 삭제 대상으로 처리한다. 저장 완료 후 불필요한 분석본과 모델 원문 응답을 정리한다. 삭제 실패는 기록하고 재시도한다.
4. **권한:** 본인만 자신의 용량과 파일을 보고 삭제한다. 이미지는 공개 주소로 제공하지 않는다.
5. **확인 기준:** 모든 파일 상태가 100MB 계산에 포함되어야 한다. 한도 초과로 기존 파일이 사라지면 안 되며 취소·방치 자료가 정해진 규칙대로 정리되어야 한다.

## 7. 사용 완료와 휴지통

1. **입력·행동:** 기프티콘·쿠폰·상품권의 `사용 완료`를 누르고, 휴지통에서 복원 또는 즉시 삭제를 누른다.
2. **정상 결과:** 사용 완료 상태가 기록되고 이미지가 휴지통으로 이동한다. 이동 후 30일이 지나면 삭제 대상이 되며 이후 정리 작업에서 실제 삭제된다.
3. **실패 처리:** 복원과 삭제가 겹치면 하나만 성공해야 한다. 삭제된 파일을 복원됐다고 표시하지 않는다. 실패 시 `삭제 실패` 상태로 남기고 재시도한다.
4. **권한:** 소유자만 사용 완료, 복원과 삭제를 할 수 있다.
5. **확인 기준:** 이미지를 복원해도 사용 완료는 자동 취소되지 않아야 한다. 30일은 실제 삭제 시각이 아니라 삭제 대상 시각이어야 한다.

## 8. 통합 홈

1. **입력·행동:** 홈에서 다가오는 기한을 전체·결제·혜택으로 필터링하고, 미니 캘린더 날짜나 일정 행을 눌러 연결 항목을 확인한다.
2. **정상 결과:** 사용자 시간대 기준 다음 30일의 KRW 예정 결제액, 다른 통화별 예정액, 결제 건수와 미사용 혜택 만료 건수가 보인다. 중앙 목록은 30일 제한 없이 관리 항목마다 가장 가까운 일정 하나씩 최대 6개를 표시하고, 월간 캘린더는 결제와 혜택 만료를 범례와 함께 구분한다.
3. **실패 처리:** 금액 미확인 일정은 0원으로 보지 않고 합계 제외 건수를 표시한다. 연·월 정밀도와 날짜 미확인 항목은 임의 날짜에 넣지 않고 정보 확인 영역에 안내한다. 데이터 조회 실패는 0원·0건이나 빈 상태로 표시하지 않는다.
4. **권한:** 본인 홈만 볼 수 있다. 공통 소식은 본인의 구독·요금제·국가·결제 경로·관심사에 맞춰 연결한다.
5. **확인 기준:** 세 요약 카드, 필터 목록과 미니 캘린더가 같은 예상 일정 계산을 사용해야 한다. 통화를 합산·환산하지 않고, 필터별 최대 6개·날짜순·상세 이동·전체 목록 이동이 동작해야 한다.

## 9. 목록·상세·수정·삭제

1. **입력·행동:** 유형·카테고리·상태·날짜·정보 지원 범위로 필터링하고 이름·날짜·금액으로 정렬한다. 항목을 열어 수정하거나 삭제한다.
2. **정상 결과:** 조건에 맞는 항목이 보인다. 상세에는 요금제, 날짜, 상태, 결합 관계, 이미지, 알림, 해지 안내와 소식이 표시된다. 수정은 미래 일정·알림·리포트와 연결된 Google 일정에 반영된다.
3. **실패 처리:** 검색 결과 없음과 불러오기 실패를 구분한다. 수정 실패 시 이전 값을 유지하고 삭제 실패 항목을 사라진 것처럼 표시하지 않는다.
4. **권한:** 소유자만 조회·수정·삭제한다. 다른 사용자의 항목 ID를 알아도 열 수 없어야 한다.
5. **확인 기준:** 필터·정렬 결과가 맞고 수정 후 연결 화면이 일치해야 한다. 다른 사용자 항목 접근은 차단되어야 한다.

### 관리 항목 삭제 흐름

관리 항목 삭제와 첨부 이미지 삭제는 서로 다른 작업이다.

#### 삭제 확인창

삭제를 누르면 다음 내용을 실행 전에 보여준다.

- 삭제할 항목 이름과 유형
- 과거 이용·가격·상태 이력을 어떻게 처리할지: `확인 필요`
- 취소할 미래 예상 회차, 내부 일정과 미발송 알림 수
- 첨부 이미지 수와 각 이미지의 보관·휴지통 처리 선택: `확인 필요`
- 연결된 Google Calendar 일정 삭제 요청 여부와 외부 삭제가 실패할 수 있다는 안내
- 결합 구독의 상위·하위 연결과 삭제로 영향을 받는 항목
- 관리 항목 자체의 복구 가능 여부와 기간: `확인 필요`

#### 삭제 후 처리

1. 내부 관리 항목 삭제가 확정되면 미래 예상 회차, 내부 일정과 아직 보내지 않은 알림은 더 이상 실행되지 않게 처리한다.
2. 과거 이력을 함께 삭제할지, 비활성 이력으로 보존할지는 `확인 필요`다.
3. 첨부 이미지는 관리 항목과 별도로 처리한다. 기존 이미지 휴지통 정책을 선택한 경우 휴지통으로 이동하고 30일 후 삭제 대상이 된다. 항목 삭제 시 이미지의 기본 선택은 `확인 필요`다.
4. 연결된 Google 일정에는 삭제를 요청한다. 내부 삭제가 성공했지만 Google 삭제가 실패하면 내부 항목을 되살리지 않고 `항목 삭제 완료 · Google 일정 정리 실패`로 표시한다.
5. 내부 삭제가 성공했지만 이미지 이동·삭제가 실패하면 `항목 삭제 완료 · 이미지 정리 실패`로 표시하고 재시도 상태를 남긴다.
6. 일부 외부 정리만 실패한 경우 전체 삭제가 실패했다고 표시하지 않으며, 실패한 부분도 숨기지 않는다.
7. 결합 구독의 상위 또는 하위 항목이 연결돼 있으면 영향을 확인창에 보여준다. 삭제를 막을지, 연결을 해제한 뒤 삭제할지의 기본 정책은 `확인 필요`다.

#### 삭제 확인 기준

- 내부 삭제, 이미지 정리와 Google 일정 정리 결과가 각각 보인다.
- 미래 회차·내부 일정·미발송 알림이 더 이상 실행되지 않는다.
- 이미지가 휴지통으로 이동했다면 30일 복원·자동 삭제 규칙이 그대로 적용된다.
- 외부 정리 실패가 내부 삭제 성공을 되돌리지 않으며, 재시도 상태를 확인할 수 있다.

## 10. 날짜·반복 일정·구독 상태

1. **입력·행동:** 최초 가입일, 다음 결제일, 갱신일, 만료일, 해지 마감일과 검토일을 입력한다. 실제 이용 상태, 자동 갱신 상태와 유지·해지·재가입 계획을 각각 선택한다.
2. **정상 결과:** 날짜와 세 상태가 서로 다른 의미로 저장된다. 가입일과 주기로 계산한 다음 결제일은 `예상 날짜`로 제안하며 사용자 확인 전에는 확정하지 않는다. 월말 반복은 원래 기준일을 유지하고 윤년·시간대·날짜 정밀도를 구분한다.
3. **실패 처리:** 날짜가 없어도 저장하되 제한되는 D-day·알림·예상 지출과 이유를 표시한다. 금융 연동 없이 결제 실패를 자동 판단하지 않는다.
4. **권한:** 소유자만 날짜와 상태를 바꾼다.
5. **확인 기준:** 1월 31일 반복은 2월 말일 뒤 3월 31일이어야 한다. 자동 갱신 해제와 실제 이용 종료가 별개로 보이고, 재활성화·재가입도 기록할 수 있어야 한다.

## 11. 내부 캘린더

1. **입력·행동:** 월간·주간·목록 보기를 바꾸고 결제·갱신·해지 마감·검토·만료·보장 종료 종류를 필터링한다.
2. **정상 결과:** 본인의 일정이 선택한 기간과 종류에 맞게 보이고, 누르면 연결된 상세로 이동한다.
3. **실패 처리:** 날짜가 없거나 정확도가 부족한 항목은 임의 날짜에 넣지 않고 상세에 이유를 표시한다.
4. **권한:** 본인만 자신의 캘린더를 본다. 소유자만 연결 항목의 날짜를 수정한다.
5. **확인 기준:** 홈·상세·캘린더의 날짜와 상태가 같아야 하며 보기·필터 변경으로 일정이 중복되거나 사라지지 않아야 한다.

## 12. 앱 안 알림과 Web Push

1. **입력·행동:** 전체 또는 항목별 알림 시점·채널을 정하고 Web Push 권한을 허용한다.
2. **정상 결과:** 기본값은 사용자 시간대 기준 3일 전과 당일 오전 9시다. 앱 안 기록을 남기고 허용된 기기에 Push를 요청한다. 오후 10시~오전 8시 외부 알림은 이후로 미루며, 그때 의미가 없어진 알림은 보내지 않지만 앱 기록은 유지한다.
3. **실패 처리:** Push를 거부·미지원하는 환경에서도 앱 안 알림은 유지한다. 실패와 결과 불명을 구분하고, 같은 작업의 중복 요청을 막는다. 날짜·기간·종료·갱신 변경 시 미발송 알림을 갱신한다.
4. **권한:** 본인만 알림 규칙과 기기 권한 정보를 관리한다.
5. **확인 기준:** 사용자 시간대와 조용한 시간이 적용되어야 한다. 실패·결과 불명·재시도가 구분되고, 외부 기기에 정확히 한 번 도착한다고 보장해서는 안 된다.

Web Push 결과 불명과 일시 실패는 최초 요청을 포함해 최대 3회 처리한다. 재시도 간격은 5분, 30분이며, 재시도 시점에 일정의 의미가 없어졌으면 `건너뜀`으로 기록한다. 브라우저·운영체제별 실제 전달 동작은 운영 환경에서 별도 검증한다.

## 13. Google Calendar 단방향 연동

1. **입력·행동:** Google 연결과 권한 제공에 동의하고 내보낼 일정 종류를 고른다. 해제할 때 Google 일정을 삭제할지 유지할지 선택한다.
2. **정상 결과:** `subscribe-manager` 전용 보조 캘린더를 만들고 선택 일정을 보낸다. 재연결은 기존 캘린더를 재사용한다. 내부 수정·삭제는 연결된 Google 일정에만 반영한다. 가능한 경우 일반 토큰 만료는 자동 갱신한다.
3. **실패 처리:** 갱신 실패·권한 철회 시 재연결을 요청한다. 실패해도 내부 일정과 알림은 유지한다. 재시도로 캘린더와 일정이 중복 생성되면 안 된다.
4. **권한:** 연결한 본인만 관리한다. Google에서 수정한 내용을 가져오는 양방향 동기화는 제공하지 않는다.
5. **확인 기준:** 최초 연결·재연결·수정·삭제·해제를 확인하고 중복이 없어야 한다. 연결 오류 중에도 내부 기능이 작동해야 한다.

최소 권한, 자동 토큰 갱신과 공개 전 OAuth 검증 필요 여부는 실제 프로젝트에서 `검증 필요`다. 심사 완료일은 미리 확정하지 않는다.

## 14. 예상 결제 일정과 지출 리포트

1. **입력·행동:** 요금·통화·주기·확인한 다음 결제일·자동 갱신 상태를 등록한다. 리포트에서 기간과 통화를 고르고 예상 청구액·월 환산액·추정 누적액을 본다.
2. **정상 결과:** 오늘부터 12개월의 예상 일정이 만들어지고 시간이 지나면 부족한 기간만 보충된다. 연간 구독의 다음 일정도 범위 안에 표시한다. 세 금액은 통화별로 나눠 계산하며 근거·기준일·제외 항목 수를 보여준다.
3. **실패 처리:** 정보가 부족하면 이유를 표시하고 중복 회차를 만들지 않는다. 예정일이 지나도 실제 결제로 확정하지 않는다. 금액 미확인은 0원으로 넣지 않고, 모두 미확인이면 `계산할 정보 없음`으로 표시한다. 서로 다른 통화를 더하지 않고 현재 요금을 과거 실제 지출처럼 사용하지 않는다.
4. **권한:** 본인만 자신의 예상 일정과 리포트를 본다. 요금·주기·날짜·갱신 상태 변경은 과거를 유지하고 미래만 갱신한다.
5. **확인 기준:** 12개월 범위와 월간·연간 일정이 맞아야 한다. 예상 청구액·월 환산액·추정 누적액이 구분되고 `확인된 월 환산액 35,000원 · 금액 미확인 구독 2개 제외`처럼 범위를 알 수 있어야 한다.

### 포함·제외와 재계산 규칙

- 기간의 시작일과 종료일은 모두 포함하며 사용자 시간대를 기준으로 한다.
- 취소·건너뜀 회차는 예정 청구액에서 제외하고 제외 사유와 개수를 표시한다.
- 금액 미확인 회차는 합계에서 제외하고 무료나 0원으로 취급하지 않는다.
- 사용자가 명확히 0원으로 등록한 회차는 금액 미확인과 구분해 0원 회차로 표시한다.
- 통화별로 따로 합산하고 자동 환율 환산은 하지 않는다.
- 날짜·가격·자동 갱신·이용 상태를 수정하면 과거 기록은 유지하고 미래 예상 회차만 갱신한다. 리포트는 저장된 과거 회차와 갱신된 미래 회차를 기준으로 선택 기간 결과를 다시 계산한다.
- 실제 결제·환불 거래의 등록과 대사는 후속 기능이며, 예정일이 지났다는 이유만으로 실제 지출로 바꾸지 않는다.
- 사용자가 예정 회차를 취소 또는 건너뜀으로 표시할 수 있으며 이는 실제 결제·환불 거래의 확정이 아니라 예상 합계 제외 설정이다.

### 리포트 확인 기준

- 같은 기간이라도 `기간 전체 예정액`과 `남은 예정액`이 구분되어야 한다.
- 지난 예정액을 포함한 합계에는 실제 결제 여부를 확인하지 않았다는 안내가 보여야 한다.
- 취소·건너뜀·금액 미확인·다른 통화의 포함 여부를 사용자가 확인할 수 있어야 한다.
- 사용자 시간대를 바꾸면 기간 경계와 오늘 기준을 새 시간대에 맞춰 다시 판단해야 한다.
- Phase 6 도입 전 가격은 근거가 없으므로 추정 누적액에 소급하지 않는다. 도입 이후 금액·통화·주기 변경 구간만 기록해 해당 구간을 계산한다.

## 15. 결합 구독

1. **입력·행동:** 직접 결제, 다른 구독에 포함된 혜택, 상위 구독을 통한 추가 요금 또는 금액 미확인 관계를 고르고 상위 구독과 비용 귀속 항목을 연결한다.
2. **정상 결과:** 상위 구독과 이용 서비스 관계가 상세에 보이며 같은 비용은 한 항목에서만 합산된다.
3. **실패 처리:** 관계만 있고 금액을 모르면 무료·할인액으로 확정하지 않는다. 잘못된 연결은 저장하지 않고 다시 선택하게 한다.
4. **권한:** 연결 항목 소유자만 관계를 만들고 변경·삭제한다.
5. **확인 기준:** 네이버플러스 멤버십을 통해 넷플릭스를 이용하는 경우처럼 결제와 이용이 일대일이 아니어도 같은 비용이 두 번 합산되지 않아야 한다.

결합 관계가 남은 상위·하위 항목은 삭제하지 않는다. 사용자는 리포트에서 관계를 먼저 해제한 뒤 항목을 삭제한다. 자기 자신 연결, 다른 사용자 항목 연결과 순환 연결은 저장하지 않는다.

## 16. 기간·전체 구독 시각화

1. **입력·행동:** 시작일·종료일·통화를 선택해 월별 증감과 전체·남은 예정액을 확인한다. 전체 구독 기간에서는 이번 달 결제 금액·구독 개월 수·누적 금액을 선택하고 버블 차트·그래프·표를 전환한다.
2. **정상 결과:** 기간 화면은 월별 라인 차트와 지난 예정액·미래 결제 예정액을 색으로 나눈 막대·표를 제공한다. 전체 기간 화면의 그래프와 표는 값 내림차순이며 버블은 이름 첫 글자 아이콘을 사용한다. 선택 상세에는 요금제, 결합 관계, 다음 결제일, 예상 비용과 상태 이력이 보인다.
3. **실패 처리:** 지난 예정액을 실제 결제로 확정하지 않는다. 금액 미확인은 무료처럼 작은 버블로 만들지 않고 작은 별도 영역에 둔다. 서로 다른 통화를 한 비용 비교에 섞지 않는다.
4. **권한:** 본인만 자신의 시각화를 본다.
5. **확인 기준:** 기간 합계·월별 라인·막대·표의 숫자가 일치하고, 전체 기간의 버블·그래프·표도 같은 수치를 사용해야 한다. 선택 상세, 내림차순, 키보드, 동작 줄이기와 모바일을 확인한다.

라인·막대그래프는 기존 SVG·HTML 방식으로 렌더링한다. 버블 차트는 D3의 중심 인력·충돌 시뮬레이션으로 원이 겹치지 않으면서 밀집된 자유 배치를 만들고, 값의 제곱근에 비례한 반지름으로 면적 차이를 표현한다. 버블 영역은 데스크톱 320px·모바일 280px을 기본으로 하되 항목 수에 따라 제한적으로 확장한다. 포인터 접근 반발, 드래그, 관성, 버블·경계 충돌을 지원하고 조작이 끝나면 감쇠해 정지한다. 드래그는 선택 클릭과 구분하며 버블·그래프·표는 선택 ID와 하단 상세 패널을 공유한다. 최소 크기 보정과 정확한 값 확인 위치를 안내한다. 각 시각화와 같은 데이터를 HTML 표로도 제공해 수치 확인과 접근 가능한 대체 보기를 유지한다.

자체 구현이 기본이다. OriginKit은 참고만 하며 라이선스·접근 조건 확인 전에는 필수로 사용하지 않는다.

가입·종료·재가입 이력은 Phase 6 도입 이후 실제 상태 변경부터 기록한다. 도입 전 이력은 현재 상태나 시작일로 추측해 만들지 않고 `이력 기록 시작`으로 구분한다.

## 17. 공식 해지 방법 안내

1. **입력·행동:** 서비스 상세에서 실제 가입·결제 경로를 선택해 해지 안내를 연다.
2. **정상 결과:** 공식 홈페이지·도움말·약관 또는 Apple·Google·통신사 등 결제 경로의 공식 자료에서 확인한 메뉴 경로, 링크, 조건, 해지 후 이용 가능 기간, 출처와 확인일이 보인다. 초기 안내와 중요 변경은 운영자(초기에는 프로젝트 소유자)가 검토한 뒤 공개한다.
3. **실패 처리:** 직접 링크를 확인하지 못하면 URL을 만들지 않고 공식 도움말과 확인된 메뉴 경로만 제공한다. 블로그·커뮤니티는 확정 근거로 쓰지 않는다. 오래되거나 바뀐 정보는 `검증 중`, `재확인 필요` 또는 `검수 대기`로 표시한다.
4. **권한:** 사용자는 공개 안내를 읽지만 실제 해지는 외부에서 직접 한다. 운영자가 안내를 공개·수정·비공개 처리한다.
5. **확인 기준:** 모든 단계와 URL에 공식 출처와 확인일이 있어야 한다. 결제 경로별 절차를 섞거나 미확인 내용을 사실처럼 보여주면 안 된다.

가격·혜택·해지 정보는 기본 7일마다 확인하고, 종료·적용일이 임박하면 하루 1회 확인한다. `임박` 기간은 `확인 필요`다.

## 18. 서비스별 최신 소식

대상은 OTT, AI, 디자인, 게임, 쇼핑·배달 멤버십, 음악·독서·강의와 가전 구독의 콘텐츠·기능·한도·가격·혜택 변경이다.

1. **입력·행동:** 구독·요금제·국가·결제 경로를 등록하고 관심 기능·혜택을 표시한다. 홈이나 소식 화면에서 관련 소식을 연다.
2. **정상 결과:** 서비스별 공통 소식을 하루 1회 확인하고 사용자마다 다시 검색하지 않는다. 제목·요약·출처·발표일·적용일·국가·요금제·조건·확인일과 내게 미치는 영향을 보여준다. 공식 출처가 확인된 소식은 자동 공개할 수 있다.
3. **실패 처리:** `검색 실패`, `새 소식 없음`, `적용 조건 미확인`, `원문 확인 실패`, `예산으로 갱신 못함`을 구분한다. AI 모델 발표와 내 요금제 사용 가능 여부를 따로 확인한다. 일부 OTT 검색 결과를 전체 편성이라고 표현하지 않는다.
4. **권한:** 사용자는 공통 소식을 읽고 본인의 관심만 관리한다. 다른 사용자의 구독·관심은 볼 수 없다. 공통 소식은 운영자가 관리한다.
5. **확인 기준:** 출처·확인일, 발표일·적용일과 적용 범위가 구분되어야 한다. 확인되지 않은 조건은 `확인 필요`이고, 검색 실패와 새 소식 없음이 다르게 보여야 한다.

## 19. 운영자의 검수와 공개

### 최소 운영 방식 추천

MVP에는 일반 사용자용 관리자 화면 전체를 바로 확정하지 않고, 운영자만 접근할 수 있는 제한된 검수 도구를 먼저 사용하는 안을 추천한다. 필요한 기능은 검수 목록, 원문·링크 열기, 상태 변경, 공개·비공개, 수정과 변경 기록 확인이다. 사용자·결제·통계까지 포함한 큰 관리자 화면을 만들지 않아도 기존 해지 안내와 소식 공개 원칙을 지킬 수 있기 때문이다.

별도 관리자 화면을 만들지, 제한된 내부 도구를 사용할지는 `확인 필요`다. 운영 방식이 확정되기 전에는 관리자 화면 개발을 MVP 필수 화면으로 확정하지 않는다.

### 운영자와 권한

- 초기 운영자는 프로젝트 소유자다.
- 추가 운영자를 지정하는 방법과 권한 범위는 `확인 필요`다.
- 일반 사용자는 검수 대기 목록, 원문 관리, 공개·비공개 버튼과 변경 기록에 접근할 수 없다.
- 운영자 작업에는 검토자, 검토 시각, 변경 전·후 내용과 상태 변경 이유를 남긴다.

### 해지 안내 상태와 처리

| 상태 | 사용자에게 보이는 결과 | 운영자가 하는 일 |
| --- | --- | --- |
| 초안 | 보이지 않음 | 공식 원문, 결제 경로, 절차와 조건을 정리 |
| 검수 대기 | 보이지 않음 | 공식 링크를 직접 열어 서비스·국가·결제 경로와 단계가 맞는지 확인 |
| 공개 | 출처·확인일과 함께 보임 | 검토자와 검토 시각 기록 후 공개 |
| 재확인 필요 | 마지막 확인일과 경고를 표시. 불확실한 단계 표시 방식은 확인 필요 | 변경된 공식 원문과 기존 안내를 비교 |
| 비공개 | 일반 사용자에게 보이지 않음 | 근거 부족·오류·중요 변경 시 숨기고 이유 기록 |

공식 원문 확인은 저장된 링크를 직접 열어 공식 도메인인지, 해당 서비스·국가·요금제·결제 경로의 안내인지, 링크와 핵심 조건이 현재도 유효한지 확인하는 방식으로 한다. 블로그·커뮤니티는 확정 근거로 쓰지 않는다.

중요 변경이 발견되면 기존 안내를 그대로 최신 정보처럼 두지 않는다. 추천안은 즉시 `재확인 필요`로 바꾸고 경고와 마지막 확인일은 보여주되, 확인되지 않은 단계는 숨기는 것이다. 기존 안내 전체를 유지할지 비공개할지는 `확인 필요`다.

### 최신 소식의 자동 공개와 운영 처리

- 공식 출처 링크가 확인되고 제목·요약·발표일 또는 적용일·대상 조건·확인일을 출처에 근거해 구분할 수 있으면 자동 공개할 수 있다.
- 대상 국가·요금제·가입 조건이 불명확하면 자동으로 사실을 보완하지 않고 `확인 필요`를 붙인다.
- 운영자는 잘못된 요약을 출처 범위 안에서 수정하고, 중복·오류·근거 부족 소식을 비공개 처리할 수 있다.
- 수정·비공개에는 운영자, 시각, 이유와 변경 전·후 내용을 기록한다.

### 운영 검수 확인 기준

- 일반 사용자가 운영 기능을 실행할 수 없어야 한다.
- 공개 해지 안내에는 검토자 기록, 확인일과 공식 출처가 있어야 한다.
- 상태 변경과 내용 수정 이력을 나중에 확인할 수 있어야 한다.
- 공식 출처 조건을 충족하지 못한 소식·해지 안내가 공개 상태가 되면 안 된다.

## 20. 직접 등록과 정보 지원 범위

초기 후보는 넷플릭스·티빙·라프텔, ChatGPT·Gemini·Perplexity, Canva·Adobe, Xbox Game Pass, 쿠팡 와우·네이버플러스 멤버십, 밀리의 서재와 LG전자 가전 구독이다.

1. **입력·행동:** 후보 밖 서비스도 직접 입력해 등록하고 상세에서 소식·해지 안내 지원 상태를 각각 확인한다.
2. **정상 결과:** 모든 서비스는 직접 관리할 수 있다. 공식 자료와 실제 동작을 확인한 서비스·결제 경로만 소식 또는 해지 안내 `지원`으로 표시한다.
3. **실패 처리:** 확인하지 못한 후보는 `직접 관리만 가능`, `자료 수집 중`, `정보 확인 필요`, `검증 중` 또는 `지원하지 않음`으로 표시한다.
4. **권한:** 사용자는 본인 항목을 관리한다. 공통 지원 상태와 공식 자료는 운영자가 관리한다.
5. **확인 기준:** 후보 밖 서비스도 등록할 수 있어야 한다. 같은 서비스의 소식과 해지 지원 상태를 따로 관리하고 검증 전에는 지원 완료로 표시하지 않아야 한다.

## 21. AI 분석·검색 한도

초기 한도는 이미지 분석 사용자당 하루 10회·US$0.20, 검색·모델 호출 서비스 전체 하루 US$2, 개발·시험 누적 US$10이다.

1. **입력·행동:** 사용자는 이미지 분석을 요청한다. 소식·해지 검색은 새로고침마다 실행하지 않고 공통 확인 주기에 따라 처리한다.
2. **정상 결과:** 횟수와 예상 비용을 확인해 한도 안에서 호출한다. 첫 모델 후보는 `gpt-5.4-mini`이며 설정으로 바꿀 수 있다.
3. **실패 처리:** 횟수·예산 중 먼저 도달한 제한을 적용한다. 예상 비용은 실제 청구와 다를 수 있음을 알린다. 한도 도달·외부 실패 중에도 직접 등록과 기존 조회는 계속 제공한다.
4. **권한:** 사용자는 본인 이미지 분석 상태만 확인한다. 전체 검색 예산과 모델은 운영자가 관리하며 다른 사용자의 이미지·결과는 공유하지 않는다.
5. **확인 기준:** 한도 초과 전에 새 호출이 막히고 새로고침으로 검색이 반복되지 않아야 한다. 제한 중에도 기본 관리 기능이 작동해야 한다.

실제 프로젝트의 모델 접근 권한, 이미지 입력·구조화 결과·웹 검색 조합, 품질과 비용은 샘플로 `검증 필요`다.
